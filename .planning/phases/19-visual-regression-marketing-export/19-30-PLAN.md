## The two stages (owner decision 2026-11-23)

Rule. A step is a stillness step (`still:`) when all it does is let what `make` built finish and hold it still, so
the page can settle at screen size: it stops a spinner or a caret's blink, or waits for a keyboard, an alert or a
glass shadow the state itself brought up, and re-focuses only a field the state itself focused. Every other step is
an operating step (`interact:`): a user's action (a tap or activation, a held tap, opening a menu or a dialog,
scrolling, typing, focusing a field the state did not focus), or a check or correction the page does not need in
order to settle (`RevealStep.showLargeTitle()` names the shown list as the bar's scroll view; a lone
`RevealStep.awaitDialogPlatter()` checks the platter of a dialog `make` presented), together with everything the same
step does after its action: a hold of what the action brought up belongs to that step, in its order. A step moves
between stages by its argument label only.

Order. Screen-sized path (committed height at or under the window's own): host, `still`, `interact`, settle,
capture, check. Tall path: host, `still`, native settle, freeze and verify, grow (status bar companion, size-class
pins, resize, one sample, geometry check), `interact`, settle, capture, check. Measuring mode: the window's own
height in a screen-sized hosting, then each taller height in a fresh tall hosting, the need read after the settle.
An operating step cannot be undone and the owner's order grows the window before it, so a taller height needs a fresh
hosting; and because the previous hosting's scroll view is gone by then, "a scroll view that does not grow with the
window" is read as the most-overflowing scroll view keeping its class and its height (within one device pixel) from
one hosting to the next while the window grew.

Keyboard rule (evidence, not guesswork). Two conditions, both read while the page is hosted, after the settle, on
the scroll view that sets the need (`PageNeed.scrollView`):
1. A keyboard is up: the frame UIKit last announced in `UIResponder.keyboardDidChangeFrameNotification`
   (`keyboardFrameEndUserInfoKey`, screen coordinates), recorded by `KeyboardWatch` from the first matrix case on, has
   a height above 0 and a top above the screen's bottom less one point. This is `GalleryScenarios.keyboardIsUp(over:)`,
   the rule the three keyboard steps already wait on, unit-tested by
   `BrowsingStepTests.testTheKeyboardIsUpWhileItsAnnouncedFrameCoversTheScreen`. The alternatives are refuted in the
   code: `KeyboardWatch`'s documentation records that a window's keyboard layout guide never read the keyboard as up,
   and the steps' comments record that the keyboard is a separate window that is not drawn, so the page's own
   hierarchy holds no keyboard view to find.
2. That scroll view avoids the keyboard: the keyboard's top lies at least one device pixel above the scroll view's
   bottom edge (in screen coordinates), and the scroll view's `adjustedContentInset.bottom` covers that overlap within
   one device pixel. This is the mechanism 19-20's experiment measured (the keyboard stays at the screen's bottom while
   the window extends below it, and the avoiding inset grows by exactly the window's growth, so the need never holds
   still). Condition 1 alone is not enough: `LoginView` ignores every safe-area region, the keyboard's too, at text
   sizes up to Large (`ignoredSafeAreaRegions`), so a page can have a keyboard up without its scroll view following it.
When both hold and the page needs more than its window, no height covers it: the measuring mode says so at that
hosting (`cannotCover`, reason `cannot-cover:keyboard`) instead of running to 12 steps, and the check appends
`, cannot-cover:keyboard` to its reason. The harness module takes the keyboard's top from the matrix as a closure
(`keyboardTop`, `nil` when no keyboard is up by condition 1), as it takes `freezeViewport`, so condition 1 stays the
one rule the steps use; condition 2 is the harness's, in `TallWindow.swift`.
