<objective>
Build the `AnalyticsClient` dependency itself — the struct of closures, the D-13 absent-credential gate, the no-op and unimplemented values, the `DependencyKey`/`DependencyValues` wiring — and the D-11 global default parameters closure it configures the SDK with.

Purpose: this plan owns the **only** SDK import in the repository (D-12) and the **only** place the D-13 gate is evaluated. Getting the gate wrong is the single most consequential mistake available in this phase: the naive reading of D-13 ("no app ID, so don't initialize") leaves every later signal call reaching an uninitialized SDK, which trips an assertion in debug builds.
Output: a usable `@Dependency(\.analyticsClient)` with gate and default-parameter behavior proven by test.
</objective>

    - **Mutability choice, made deliberately:** the properties are `var`, not `let`. `HapticsClient` (the D-12 template) uses `let`, but the repository's established signal-capture idiom builds a spy by taking `.noop` and mutating one field, and this client will be overridden at roughly 130 existing test sites. `var` lets a test override `send` while leaving `start` inert.     - `AnalyticsClient.noop` has both closures empty. `AnalyticsClient.unimplemented` has both closures built from `IssueReporting.unimplemented(placeholder:)`, matching the template exactly.

    - **The D-13 gate:** `live` reads `AppInfo.telemetryDeckAppID` once. When it is nil, `live` **is** `.noop` and the SDK is never referenced. This one check covers contributor builds, forks, CI, the test host and previews, and it is simultaneously what stops a signal from reaching an uninitialized SDK.
    - **Second guard for the initialization race:** when an app ID *is* present, `live` captures a `Synchronization.Mutex<Bool>` initialized false. `start` builds the SDK config, initializes, then sets it true. `send` returns without touching the SDK while it is false. Without this, a signal emitted between process start and the launch-finish action would reach an uninitialized SDK and trip its assertion.
    - Per D-10, the SDK's built-in anonymized identifier is used as-is: `start` never assigns a default user, `send` never passes a custom user identifier, and nothing calls the SDK's user-identifier update function. All three are recorded opt-outs in `COVERAGE.md`.
    - `start` builds the SDK config from the app ID and, if D-17 chose one, the salt. It assigns `AnalyticsDefaultParameters.live` to the config's default-parameters closure, then initializes. Every other config knob keeps its SDK default per `COVERAGE.md` — `sendNewSessionBeganSignal`, `sessionStatsEnabled`, `testMode`, `swiftUIPreviewMode`, `reservedParameterWarningsEnabled` and `logHandler` are all deliberately left alone.
    - `send` switches on the signal's `Rendered` value: the plain case forwards name and parameters to the SDK's signal function; the error case forwards the identifier and the category to the SDK's error preset, translating the local `AnalyticsErrorCategory` mirror into the SDK's own category enum by raw value. The SDK's deprecated manager-prefixed spellings are never used — this project does not accept deprecation warnings.
