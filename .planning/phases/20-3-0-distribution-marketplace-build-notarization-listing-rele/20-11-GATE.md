## The check name

`snapshot-gate.yml` as it stands on `feature/gsd-phase-19` (read with `git show`, never checked out) has the verdict
job `aggregate` (`needs: [checks, build, shard, triage, retry, native-policy]`, `if: always()`), with no `name:` of
its own, so its check run is named `aggregate`. The workflow runs on every `pull_request`, so a merged release PR's
head commit has that verdict. The check run belongs to GitHub Actions, which the script requires (T-20-30).

The name is `aggregate`, held once per workflow as `SNAPSHOT_GATE_CHECK` in `deploy.yml` and `deploy-pal.yml`.

Deviation from the plan's test wording ("test reads it from the file"): the file is not on this branch until Phase 19
merges through `main`, and it is not copied here. So the tests (a) require both workflows to carry the same name,
`aggregate`, the value read from Phase 19's file, and (b) read the name from `snapshot-gate.yml` when the file is
present (it is skipped, visibly, while the file is absent) and require it to equal both workflows' name. The
comparison with the real file therefore starts running by itself when Phase 19's workflow arrives. If 19-10's
`aggregate` job is renamed before it merges, the test fails and the constant is updated.

## What Task 2 added

- `actions-tool/require-snapshot-gate.sh <sha> <check name>`: reads
  `gh api --paginate repos/$GITHUB_REPOSITORY/commits/<sha>/check-runs`; passes only when there is at least one check
  run of that name from GitHub Actions and every such run is `completed` with the conclusion `success`. `neutral`,
  `skipped`, `cancelled`, `timed_out`, `failure`, `action_required`, `stale`, a run still `queued` or `in_progress`,
  a same-named run from another app, no run at all and a failed API call all exit 1, naming the commit and the state.
  A non-SHA, an empty name or an unset repository also exit 1 before any call.
- `deploy.yml`: step "Require the screenshot check" right after Checkout (before the build-number check and "Check
  release notes"), on `github.event.pull_request.head.sha`; the job now declares `permissions: contents: write,
  checks: read` (it had no block; `contents: write` is what its push and release need).
- `deploy-pal.yml`: the same step in the `submit` job on `github.sha`; the job's permissions gain `checks: read`.
- Tests: `test_require_snapshot_gate.py` (fake `gh`), and in `test_workflows.py` the step's place, SHA, token and
  permissions in both workflows, and the shared check name.

## Points for the owner and Task 3

1. `github.sha` of a PAL dispatch is the dispatched commit. The gate runs on pull requests, so a check run exists on a
   pull request's head commit, not on a squash or rebase commit that lands on `main` (history on `main` is linear).
   The PAL submission therefore passes only when it is dispatched on a commit that carries the verdict (for example the
   release PR's head), or when Phase 19's gate also runs on `main`. Task 3 should settle which, and whether the PAL
   step should look up the commit's pull request instead.
2. A candidate-mode run (push to `ci/snapshot-gate`) is also a check run named `aggregate` on its commit and passes
   without comparing anything. The latest run per name is what GitHub returns, so a candidate run on the same commit
   as a release PR's head could stand in for a compare run. The branch is used before the file reaches the default
   branch only, so this is a note for Phase 19's closure, not a change here.
3. actionlint is at `/opt/homebrew/bin/actionlint` on this machine; `$HOME/.local/bin/actionlint` does not exist.
