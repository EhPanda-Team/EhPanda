## The check name

`snapshot-gate.yml` as it stands on `feature/gsd-phase-19` (read with `git show`, never checked out) has the verdict
job `aggregate` (`needs: [checks, build, shard, triage, retry, native-policy]`, `if: always()`), with no `name:` of
its own, so its check run is named `aggregate`. The workflow runs on every `pull_request`, so a merged release PR's
head commit has that verdict. The check run belongs to GitHub Actions, which the script requires (T-20-30).

The name is `aggregate`, held once per workflow as `SNAPSHOT_GATE_CHECK` in `deploy.yml` and `deploy-pal.yml`.

Deviation from the plan's test wording (first checked against `main` at the merge: the name test now runs, passes, and
`aggregate` is the job's ID with no `name:`) ("test reads it from the file"): the file is not on this branch until Phase 19
merges through `main`, and it is not copied here. So the tests (a) require both workflows to carry the same name,
`aggregate`, the value read from Phase 19's file, and (b) read the name from `snapshot-gate.yml` when the file is
present (it is skipped, visibly, while the file is absent) and require it to equal both workflows' name. The
comparison with the real file therefore starts running by itself when Phase 19's workflow arrives. If 19-10's
`aggregate` job is renamed before it merges, the test fails and the constant is updated.

## What Task 2 added

- `actions-tool/require-snapshot-gate.sh <sha> <check name>`: reads
  `gh api --paginate repos/$GITHUB_REPOSITORY/commits/<sha>/check-runs`; passes only when there is at least one check
  run of that name from GitHub Actions and every such run is `completed` with the conclusion `success`. `neutral`,
  `skipped`, `cancelled`, `timed_out`, `failure`, `action_required`, `stale`, a run still `queued` or `in_progress`,
  a same-named run from another app, no run at all and a failed API call all exit 1, naming the commit and the state.
  A non-SHA, an empty name or an unset repository also exit 1 before any call.

  release notes"), on `github.event.pull_request.head.sha`; the job now declares `permissions: contents: write,

- `deploy-pal.yml`: the same step in the `submit` job on `github.sha` (changed by point 1 below: `--merged-pr`); the job's permissions gain `checks: read`.

## Points for the owner and Task 3: settled

### 1. PAL `github.sha` against the pull request head: a real gap, fixed

Evidence (read 2026-11-11, `EhPanda-Team/EhPanda`):

- `main` is linear: the last eight commits each have one parent. PR 460 (head `87841ed5d`) is merged as
  `be6157993`, PR 457 (head `3b1f61e40`) as `b04cb72eb`: the commit on `main` is never the PR head, so the history
  is squash or rebase. The repository's `allow_*_merge` settings are not visible to this login (the API returns
  null), so the style is read from the history, not from the settings.
- `snapshot-gate.yml` triggers on `pull_request`, `workflow_dispatch`, `workflow_call` and a push to
  `ci/snapshot-gate` only. A push to `main` does not run it, so a commit on `main` has no `aggregate` check run.
- `deploy-pal.yml` is `workflow_dispatch`-only and its submit job checked `github.sha`. Dispatched on the release's
  commit on `main` it would always stop with "no 'aggregate' check run", whatever the PR's verdict. (Live: the gate
  script on `be6157993`'s PR head and on `8e516ec22`, below.)

Fix, smallest that works (TDD: RED `02c28dc6c` (script) and `09dcb5907` (workflow steps), GREEN `3894ab458`): `require-snapshot-gate.sh` gets
`--merged-pr`. It reads `gh api repos/<repo>/commits/<sha>/pulls`, takes the one merged pull request whose
`merge_commit_sha` is `<sha>`, and reads the verdict on that PR's head. No such PR, an unmerged one or more than one
fail. `deploy-pal.yml` passes it. Why not "dispatch on a SHA that has the verdict": the version check already demands
the release commit, which is the commit on `main`; asking the operator to dispatch on the PR head would make the
workflow build a commit that is not on `main`. `deploy.yml` needs nothing: it already reads the merged PR's head
(`github.event.pull_request.head.sha`). A dispatch on a commit with no merged PR (a direct push, a later docs commit)
is refused on purpose: the PAL build must be the commit the gate judged.

### 2. `aggregate` shadowing by candidate-mode runs: a real gap, fixed

`snapshot-gate.yml` on `main` (read, not edited) decides the mode in the `checks` job: `inputs.mode` if given;
otherwise `compare`, or `candidate` for a push to `ci/snapshot-gate` while no `fingerprints.json` exists. A candidate
run's `aggregate` job passes when its shards recorded their pictures, and it is an `aggregate` check run from GitHub
Actions on the pushed (or dispatched) commit. A release reads "latest `aggregate` is `success`" by name, so a
candidate run on a release PR's head would stand in for a compare run (a spoof, and also an accident the owner's own
baseline recording could cause). Live: `c560ead1d`'s `aggregate` belongs to run 42727781967, event `push`, branch
`ci/snapshot-gate`.

Fix: `--compare-only`. The script reads the workflow run behind each matching check run (the run ID in its
`details_url`, then `gh api repos/<repo>/actions/runs/<id>`) and requires its event to be `pull_request`. A pull
request run has no `mode` input, so the gate's `checks` job always makes it a compare run; no event but
`pull_request` can start one without the owner or a pusher choosing the mode. Both workflows pass it (so the script,
not the workflow YAML, holds the rule), and both jobs gain `actions: read` for the run lookup. `snapshot-gate.yml` is
unchanged. The option is `--compare-only` rather than `--event pull_request` because `deploy-pal.yml`'s own test
forbids the word `pull_request` in that file (it guards "dispatched by hand only"); that assertion is untouched.

### 3. Release-time gate call on `main`

`main`'s `deploy.yml` and `deploy-beta.yml` also call `snapshot-gate.yml` as a reusable workflow in compare mode, and
`Deploy` `needs` it (19-10). That call's check run is named `snapshot-gate / aggregate`, a different name, so it
neither satisfies nor spoils this step. `deploy.yml` therefore runs both: Phase 19's full compare in the release run,
and this step's read of the PR head's own pull-request verdict. The plan said "the release never runs the gate"; `main`
now does (owner-approved in Phase 19), and the merge kept both. The extra step is cheap, still correct and needs
no change; whether to drop it is the owner's call. `deploy-beta.yml` has no step of this plan's.
