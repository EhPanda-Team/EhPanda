## 1. Summary

The site's report form is a plain HTML form with no CSRF token, so a native client can post exactly what the browser
posts. One GET of `?report=other` returns every type value plus the shared email and details fields, which is enough
to decide "ready" or "unavailable". The POST URL and body are fully determined by the gallery URL, the type and the
two text fields.

The app already has every route piece: the per-gallery report URL builder, the moderation delegate that opens the
report page, the fallback web sheet, and a form-POST request pattern with a stub-protocol test harness. Five
findings change the plan:

- **F-1:** The shared `fetch(_:in:attempts:)` retries a failed request up to four times. A report must not be
  retried automatically, or one tap could file several reports. `SendReportRequest` passes `attempts: 1`.
- **F-2:** The UI-test stub protocol answers every `/g/` path with `GalleryDetail.html`, so `?report=` must be
  routed before that branch, or the form will parse a gallery page and show "unavailable".
- **F-3:** The site's reply to a submitted report has never been captured. Owner msg 1933 forbids a real
  submission, and the live check blocks the POST, so how "sent" is classified rests on an assumption (OQ-1).
- **F-4:** The remembered-email note appears only on the DMCA page, and guest pages carry an empty `r_email`.
  Whether a signed-in page fills `value=` is unconfirmed until the live check runs signed in.
- **F-5:** DetailFeature uses the string catalog's generated symbols (`.commentReportConfirmTitle`,
  `.commentReportConfirmBody(_:_:)` in `CommentModeration.swift:137-147`). Deleting a catalog key therefore breaks the
  build while code still uses it. The retired keys go in the plan that comes after the alert's removal (18.1-04), and
  the new keys must exist before any view uses them (18.1-02 before 18.1-04).

## 4. Design for the plans

### 4.1 Parser (`ParserFeature`)

`Parser.parseReportForm(doc:) throws(AppError) -> ReportForm`. A `ReportForm` holds:
- `types: Set<ReportType>`: the option values of `select#report_type` that map to `ReportType` (`child`, `other`);
  everything else is ignored;
- `email: String`: the `#r_email` `value`, trimmed;
- `hasDetails: Bool`.

It throws `.parseFailed` when the form, select, email input, details textarea or `sendreport` submit is missing.

`Parser.parseReportSubmission(doc:)` returns `.sent` when `#reportform` is absent and `.rejected` when present
(DD-03). With no capture of the real reply, the rule is deliberately narrow: a page that still shows the form is never
reported as sent.

### 4.2 Requests (`NetworkingFeature`)

- `ReportFormRequest(url:, urlSession:)` sends a GET to the URL that DetailFeature builds with
  `CommentReportTarget.reportURL(for:type: .other)` from a validated gallery URL, and returns a `ReportForm`. A
  non-2xx status or a parse failure is `.unavailable` at the reducer.
- `SendReportRequest(url:, type:, email:, details:, urlSession:)` sends a POST with the form-encoded body
  `report_type`, `r_email`, `r_details`, `sendreport=Send Report`, using `attempts: 1`. It returns `.sent` or
  `.rejected`; a transport error or non-2xx status throws.
- The app's shared URL session carries the account's cookies, as comment posting does. The Report form sends no
  cookie of its own and reads none.

### 4.3 Reducer (`DetailFeature/Moderation/ReportFormFeature.swift`)

State:
- the comment: `author`, `date`, `text` (the form opens only from a comment; there is no other origin);
- `site`, `galleryURL`;
- `phase`: `.loading`, `.ready`, `.sending`, `.sent` or `.unavailable`;
- `reason?`, `email`, `details`, `prefill`;
- `emailInvalid`, `showsSpinner` (set after 0.3 s), and an alert (failed);
- `destination` (`.reportPage(URL)`).

Derived values:
- `reasons`: always `[.child, .illegal]` (D-04, D-06).
- `canSend`: a reason, a non-empty email, and details beyond the prefill.
- `isEdited`: drives `.interactiveDismissDisabled`.
- `buttonKind`: `send`, `sending`, `done` or `openReportPage`.

Actions: `task`, `loaded`, `reasonTapped`, the email and details bindings, `primaryTapped` (one action for the pinned
button and ⌘↩), `sendResponse`, the alert's `retry`, `openReportPage` and `cancel`, and `closeTapped`.

Dependencies:
- `reportFormClient`, a `@DependencyClient` with `load` and `send`;
- `continuousClock` (the 0.3 s delay);
- `dismiss`.

The success haptic is the view's `.sensoryFeedback(.success)` (C-13), not a reducer effect.

A form loaded without both `child` and `other` is `.unavailable`. `buttonKind` is `openReportPage` only when
unavailable.

### 4.4 View (`DetailFeature/Moderation/ReportFormView.swift`)

C-13, item by item:
- `NavigationStack`, with `Form` inset grouped and the intro as plain text.
- Reason rows are buttons with a trailing checkmark and `.isSelected`.
- The email field takes the keyboard modifiers C-13 lists. Details is a vertical `TextField` with `.lineLimit(5...)`
  and gets focus once a reason is picked.
- `.safeAreaBar(edge: .bottom)` holds one `.glassProminent` large button, with `.keyboardShortcut(.return,
  modifiers: .command)` and no background; the scroll view sets `.scrollEdgeEffectStyle(.soft, for: .bottom)`.
- Sent: the content is replaced by the success block, with `.sensoryFeedback(.success)` and focus moved to the title.
- Unavailable: `ContentUnavailableView`, with no actions inside it.
- Failed: an alert (`retry`, `comment.report.open`, `cancel`) attached to the form.
- iPhone uses the large detent; iPad uses the system form sheet.

### 4.5 UI-test states (DEBUG only)

`EHPANDA_UITEST_REPORT_SCENARIO` is read inside `#if DEBUG` by the stub protocol, in stubbed launches only:
- `ready` (default): the GET returns `ReportOther.html` and the POST returns `ReportSentStub.html`.
- `slowLoad`: the GET is held about 2 s (frame 31).
- `holdSend`: the POST is held about 3 s (frame 27).
- `failSend`: the POST returns 503 (frame 29).
- `unavailable`: the GET returns a page without the form (frame 30).

The request log proves which requests were made. Each state UI test asserts its screen by accessibility identifiers
and the visible copy keys.

## 5. Proxyman live check (D-13)

- **Tooling:** Proxyman CLI 1.11.0 is at `/Applications/Proxyman.app/Contents/MacOS/proxyman-cli`. The app was not
  running at research time: `proxy-host` reports port 9090, and other commands return `app_not_running`. The
  checkpoint's first step starts the app.
- **Blocking:** `proxyman-cli rules block-list create <url> --method POST --match regex --name ehpanda-report-block`.
  It takes `--method`, so the form's GET still loads while the POST is stopped. Regex:
  `^https://(e-|ex)hentai\.org/g/\d+/[0-9a-z]+/\?report=.*`. Then run `proxyman-cli block-list on`.
- **Leak probe first:** POST through the proxy (`curl -x <proxy-host>`) to the report URL of a nonexistent gallery
  (`/g/1/0000000000/?report=other`). The probe must be blocked; if it leaked, it would file nothing real.
- **Simulator routing:** the simulator uses the Mac's system proxy (`proxyman-cli proxy on`). HTTPS needs Proxyman's
  root certificate in the simulator (Proxyman's "Install for iOS Simulator", or `xcrun simctl keychain <udid>
  add-root-cert`) and SSL proxying enabled for `e-hentai.org` / `exhentai.org` (`rules ssl-proxying`).
- **Evidence:** the blocked POST appears in Proxyman's session with URL, method, form fields and a cookie header
  (checked present, never recorded). Captures stay local; the summary records field names and redacted values only.
- **Cleanup:** delete the rule, turn the block list off, and turn the system proxy off (`proxy off`), restoring
  whatever proxy state was found before the check.

## 6. Pitfalls

- **P-1:** The automatic retry (F-1).
- **P-2:** Stub routing order (F-2).
- **P-3:** Focusing Details on open hides the reasons behind the keyboard. Focus moves only after a reason is picked
  (C-13).
- **P-4:** A `.background` on the bar contradicts owner msg 1965. The lint-free way to check is a source grep in the
  plan's verify step.
- **P-5:** Removing the retired keys fails `18-copy-check.py` until the script knows they are retired, and it breaks
  the build while code still uses their symbols (F-5). The removal and the script change go together in 18.1-04,
  after 18.1-03 has removed the alert.
- **P-6:** `CommentModerationUITests` and `CommentModerationReducerTests` assert the old alert, so they are updated
  in the same plans that remove it.
- **P-7:** The fallback web sheet has to be presented over the form sheet (a nested sheet), not in place of it, so
  that closing it returns to the kept form.

## 7. Open questions

- **OQ-1 (for the owner or Pluso; non-blocking, default DD-03):** what does the site return after a successful report?
  No capture exists, and owner msg 1933 rules out a real submission. The default reports success only when the reply
  no longer shows the form, so a reply that re-shows the form after a successful report would show "Couldn't Send
  Report". That errs towards a second report rather than a false "Report Sent".
- **OQ-2:** whether a signed-in page pre-fills `r_email` (F-4). The live checkpoint observes it if the simulator is
  signed in, and the code handles both cases.
- **OQ-3 (resolved):** the copy was a draft; the owner approved it in msg 1975, without the gallery-only strings
  (D-09). Plan 18.1-02 runs without a gate.
