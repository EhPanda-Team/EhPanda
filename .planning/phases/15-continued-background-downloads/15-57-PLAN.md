<objective>
15-56 made the durable arm honest: a partially-missing record now validates into an immediately
resumable state. What remains of G-15-5 is the refusal family — the shapes where blanking is not
licensed (wholesale absence, failed scans) and the record stays complete-claiming under a transient
`.error` — plus the two predicate defects the diagnosis ordered swept: Detail's repair predicate
demands a zero completed count that can never hold at validate time, and a row-retry gating
predicate exists with zero consumers.

This plan is the affordance half. The diagnosis found the needed repair-starter already built:
`retryPages(gid:pageIndices:)` clears the failure state including `validationErrors`, pins `.repair`
with a page selection, enqueues and schedules. The inspector merely hardcodes the failed-page set
into it, and externally-missing pages derive `.pending`, not `.failed` — so the one enabled action
for the refusal family re-runs Validate forever. Widening the retry basis to failed-plus-pending for
exactly the `.error`/fileOperationFailed shape turns the dead end into a start button that works for
every refusal shape, including all-pages-missing, because the page selection travels explicitly and
never depends on the record's honesty.

Purpose: give every remaining unstartable shape its start, and sweep the predicates the diagnosis
named so no gate keys on an accident again.
Output: the widened inspector retry basis (D-G5C-01), the honest-incomplete Detail predicate
(D-G5D-01), the dead predicate deleted, and production-path tests pinning each boundary.
</objective>

## Decisions this plan makes

**D-G5C-01 — the widened retry basis.** `DownloadInspection.retryablePageIndices` returns the failed
page indices, unioned with the pending page indices exactly when
`download.displayStatus == .error && download.lastError?.code == .fileOperationFailed`. The
enabled-state gate becomes `canRetryPages` (non-empty basis), replacing the failed-only gate, and the
button sends the same computed basis. Why this shape and only this shape: at `.error` the Resume path
is hard-closed (`togglePause` rejects `.error` by design), so pending pages there have no other
route; everywhere else pending pages are exactly what Resume exists for, and widening would create a
second, page-selection-shaped resume. The union also keeps today's behavior byte-identical for the
plain failed-pages case.

**D-G5D-01 — Detail's repair predicate reads record honesty.** `downloadNeedsRepair` requires
`badge.progress.completedPageCount < badge.progress.pageCount` (with the existing `.error` status
and fileOperationFailed code conjuncts) instead of `== 0`. An incomplete record beside a file-shaped
failure resumes in place — destroying landed pages was never the right default — and the old `== 0`
held only after a repair run's blanking loop had already emptied the record, never at the moment a
user faced the button. A complete-claiming record keeps `.redownload`: its claims are wholesale
unverifiable (refusal family) or its files are present-but-wrong (corrupt-in-place), and a
presence-based repair fixes neither; the inspector's D-G5C-01 retry is the surgical alternative for
the former. Zero-completed records satisfy the new predicate trivially, so the swept case is a
strict superset of the old one.

**Label decision, recorded for the owner:** the retry button keeps its existing localized label. The
gap's truth demands a working start affordance, not copy; a label rename fans out across every
catalog locale and is reversible in isolation. If the owner wants the label to name missing pages
too, that is a one-key follow-up.
