<objective>
Close CR-02 (verification gap 3): `deleteFolder(name:)` is the un-swept sibling of the 15-63 rename confinement fix. It passes the raw, unnormalized name straight to `storage.userFolderURL(name:)` (Folders.swift:97) — plain path appending — then to `storage.removeFolder(at:)`, whose guard is lexical prefix containment only (Operations.swift:379-388): it stops `..` and absolute paths but ADMITS any nested path under the root, so a name like a user folder joined to a gallery folder recursively deletes that gallery. None of `renameUserFolder`'s refusals apply, and the recovery path diverges from the manifest: cleanup keys on an exact `parentFolderName == name` match (Folders.swift:102) that a nested name never satisfies, so `downloadIndex`, the queue store, and the background-task store keep entries for a gallery whose folder was just erased.

Sweep EVERY user-folder filesystem operation that takes a caller-supplied name — delete, create, the move's destination parent, enqueue's parent-folder creation, and any future sibling — through the one store-owned boundary, rather than fixing `deleteFolder` alone. Make `userFolderURL(name:)` unreachable as a mutation target so the next sibling cannot regress.

Purpose: no destructive folder operation from unconfined input; record/disk convergence on every exit (SC3's no-lost-work).
Output: a store-owned confined delete, a hardened shared removal primitive, a full mutation-caller sweep, and an argument-driven delete escape suite with record-convergence assertions.
</objective>
