<objective>
Rebuild the `BackgroundProcessingClient` module as a continued-processing **session** seam: a
three-endpoint client backed by a main-actor-confined store that is the only code in the tree
allowed to touch the system task scheduler.

Purpose: SC4 requires a testable client seam with an unimplemented `testValue` and no reducer
or coordinator touching the scheduler directly. D-04 fixes the shape: callers pass localized
strings and progress counts, and session events come back on a self-finishing stream. The
store exists because the system task object and its `Progress` are non-`Sendable` and
system-owned — registering with the main queue and confining every touch to the main actor is
what makes that safe without the escape hatches this repo bans at error severity.

Output: a new main-actor store file, and a rewritten client seam whose live closures are thin
hops onto it.
</objective>

Create `AppPackage/Sources/BackgroundProcessingClient/ContinuedProcessingSession.swift`
containing two public declarations plus a file-local `private let logger` built the same way
the module's existing file builds one.

Declare `public enum BackgroundProcessingEvent: Equatable, Sendable` with exactly three cases:
`granted`, `expired`, `unavailable`. Document each: `granted` means the system started the
task and the card is live; `expired` means the session ended and — per the SDK — a user tap on
the card's cancel affordance and a system resource reclaim are indistinguishable, so callers
get one signal for both; `unavailable` means the session never started (registration refused,
submission threw, or the process is running where background processing is unsupported) and is
silent by contract.

Declare `@MainActor public final class ContinuedProcessingSession` with a `public static let
shared` and a private initializer. Private stored state: the optional
`BGContinuedProcessingTask`, the optional `AsyncStream<BackgroundProcessingEvent>.Continuation`,
an `isAwaitingTask` flag covering the window between submission and the launch handler firing,
a `didCancelStaleRequests` one-shot flag, and the last pushed `totalUnitCount` and
`completedUnitCount` as `Int64` so a task adopted after the first progress push is seeded
rather than starting at zero.

`public func start(title: String, subtitle: String) -> AsyncStream<BackgroundProcessingEvent>`:
1. Guard that no session is live or pending (task nil, continuation nil, not awaiting). On
   re-entry return an immediately finished stream built with `AsyncStream { $0.finish() }` —
   the repo's idiom for an empty stream, and the same default the download façade uses.
2. Build the stream with `AsyncStream.makeStream(of:)` and store the continuation before
   anything can yield.
3. On the first call of the process only, call the scheduler's cancel-all-requests API and set
   the one-shot flag. This clears any request left pending with the system by a previous build
   whose handler no longer exists; the app submits exactly one kind of request now, and the
   single-session guard means we can never cancel one of our own live submissions. Document
   that reasoning inline — it looks like an over-broad call otherwise.
4. Resolve the bundle identifier from `Bundle.main`. If it is absent, finish with `unavailable`
   and return; never force-unwrap (`force_unwrapping` is at error severity).
5. Mint the identifier as the bundle identifier, then a literal `.continued.` segment, then a
   fresh `UUID().uuidString`. It must be freshly minted per session: a second registration of
   the same identifier kills the app, and handlers can never be unregistered. Never derive the
   suffix from a clock.
6. Register a launch handler for exactly that identifier, passing the main queue. The handler
   casts the delivered task to `BGContinuedProcessingTask` and adopts it; a failed cast
   completes the task unsuccessfully and finishes with `unavailable`. The handler must return
   immediately — adopting, seeding progress, installing the expiration handler and yielding
   `granted` is all it may do. Never loop or sleep inside it; with main-queue delivery that
   would freeze the UI.
7. If registration returns false (the identifier is not permitted by the Info.plist), finish
   with `unavailable` and return the stream.
8. Build a `BGContinuedProcessingTaskRequest` with the identifier and the caller's title and
   subtitle, set its strategy to `.queue` (D-03: a request the system cannot start immediately
   waits behind other work rather than failing, which matters because no fallback tier exists),
   and submit inside a `do`/`catch`. On throw, log the error and finish with `unavailable`.
   Never `try?` — `optional_try` is at error severity.
9. Set `isAwaitingTask` before returning the stream.

Adoption: store the task, seed `task.progress.totalUnitCount` and `completedUnitCount` from
the last pushed values, install an expiration handler that does nothing but perform the
terminal transition with `expired`, clear `isAwaitingTask`, and yield `granted`.

`public func updateProgress(completedUnitCount: Int64, totalUnitCount: Int64, subtitle: String)`:
record both counts as the last pushed values (so a later adoption seeds correctly), then, if a
task is live, assign `totalUnitCount` first and `completedUnitCount` second so the fraction
never transiently exceeds one, and call `updateTitle(_:subtitle:)` passing the task's existing
title and the new subtitle. Do not create child `Progress` objects. Add a doc comment stating
that the caller owns clamping and monotonicity — this client is domain-agnostic by D-04, and
progress-total recomputation policy belongs to the download domain. Also state that steady
progress reporting is a liveness requirement, not decoration: the scheduler forcibly expires
tasks that appear stalled and prioritizes terminating tasks reporting minimal progress.

`public func finish(success: Bool)`: perform the terminal transition with no event, i.e. mark
the task completed with the given success flag and finish the stream.

Private terminal transition helper: nil the task and the continuation **before** calling
`setTaskCompleted` or finishing the stream, so exactly one terminal transition can ever run
per session; then complete the task if one was held, yield the event if one was supplied, and
finish the continuation. Clear `isAwaitingTask` and reset the last pushed counts. Document
that the system clears the expiration handler once it fires or once completion is called, so a
late completion on an expired task is harmless but local state must still be reset.

Concurrency: the class is `@MainActor` and registration passes the main queue, which is what
makes confining the non-`Sendable` task object and its `Progress` sound. If the compiler
rejects isolation inheritance for either the launch-handler closure or the expiration-handler
property (the imported signature may mark them `@Sendable`), wrap the closure body in
`MainActor.assumeIsolated` and comment that main-queue delivery is what makes the assumption
sound. Do **not** reach for an unchecked-`Sendable` conformance or an unsafe-nonisolated
annotation, and do not add a lint exemption; if neither isolation inheritance nor the
assume-isolated form compiles, stop and raise it with the owner.

Do not add any availability annotation. The package platform floor and the app deployment
target are already at or above the API's floor, so `@available` scaffolding would be dead code.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| actor-isolated caller → main-actor store | Only `Int64`, `String` and `Bool` cross; the non-`Sendable` system task and its `Progress` never leave the main actor. |
| app process → `BGTaskScheduler` daemon | Registration and submission cross here; the identifier is bundle-prefixed and per-session. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-05 | Tampering | `BGContinuedProcessingTask` and its `Progress` inside `ContinuedProcessingSession` | medium | mitigate | The store is `@MainActor`, registration passes the main queue, and only `Sendable` scalars cross the seam. The repo's banned-unchecked-Sendable rule at error severity enforces it, and the acceptance criteria grep for both escape spellings. |
| T-15-02 | Denial of Service (self-inflicted) | system scheduler's pending-request queue | medium | mitigate | A one-shot cancel-all-requests call before the first submission of the process clears any request left by a previous build whose handler is gone. Guarded by a per-process flag so it can never cancel one of this process's own submissions. |
| T-15-03 | Elevation of Privilege | minted task identifier | medium | mitigate | The identifier is the runtime bundle identifier plus one fixed semantic segment plus a fresh UUID, so it can only ever match the Info.plist wildcard scoped to this app. No wildcard is ever passed to `register`. |
| T-15-09 | Denial of Service (app termination) | scheduler registration | high | mitigate | A second registration of the same identifier terminates the app. Mitigated by minting a fresh UUID per session and by the store's single-session re-entry guard; the coordinator adds a second guard in plan 15-05. |
| T-15-SC | Tampering | package-manager installs | low | accept | This phase installs no packages; RESEARCH.md § Package Legitimacy Audit records zero entries. |
