Close blocker G-15-26 (SC2, and SC1 through D-11). Independently re-derived in source at HEAD
6a0059d4 in BOTH directions, including running the reviewer's own falsification test against
source, which did not falsify it:

The proof `prepareWorkingSeedAnnouncingProgress` records — this run's working folder cannot
supply the pages its manifest claims — is a fact about the RUN. It is written only under the
live-session binding, and into a SESSION-scoped set that both session start
(`DownloadClient+ContinuedSession.swift:228`) and session teardown (`:363`) clear. The only other
additive writers are the two snapshot-sourced merges (`:287`, `:573`), and the snapshot's
incomplete-gallery set is built from the record's own incompleteness (`:165`), which by
construction cannot contain a complete-reading record. So the insert is the only admission this
family can ever reach, it fires only when a session is already live, and a run whose proof was
discarded can never regain it. The preparation runs exactly once per run (one production call
site, `+ExecutionPerform.swift:29`, plus one testing forwarder).

Two production orderings therefore still produce G-15-23's zero-progress card:

1. **Unavailable teardown with the queue still running.** That event arm calls the teardown and
   nothing else; its own doc says the queue runs foreground-only. The in-flight repair keeps
   running with its trust erased. This is not exotic: the session type yields that event from
   four places, three of them inside its own start — a missing bundle identifier, a refused
   registration, a throwing submission — so any scheduler refusal ends the session while the
   queue continues.
2. **A run that started before any session existed.** The live client resumes the persisted queue
   at launch (`DownloadClient.swift:83-87`), and D-07 forbids that path from starting a session —
   confirmed by enumerating every session-ensure call site; the launch resume is not among them.
   A persisted-queue gid whose record reads complete while its files are gone resolves to the
   repair mode, prepares its seed with no session id, and inserts nothing at all.

**Why this plan follows 15-47 rather than sharing a plan with it.** Both gap records require the
run-scoped proof and the announcement gate to be derived from ONE expression. That is a
directional constraint: the proof records the predicate, so the predicate must already be a
single derived expression before its lifetime can be re-owned. 15-47 established it; this plan
binds to it and its criteria forbid introducing a second one. The reverse order would have forced
two edits to the same recording site.

**The verifier's standing caution, adopted as this plan's central risk.** The reviewer's remedy
shape is sound, but its retirement points must be DERIVED against the run's exits before it is
adopted, because a proof that outlives its run re-credits a LATER redo of the same gid and
reopens D-G4-01's ceiling from the other side. That is why a lifetime regression is one of the
three required cases rather than an optional extra.

Purpose: the card reflects real work for a repair whatever the session lifecycle did around it
(SC2, D-06/D-10's queue-wide basis), and the maximally-stalled reading D-11 punishes cannot be
manufactured by a session teardown or a cold launch (SC1).
Output: a run-scoped proof with a derived lifetime, seeded where the first push can see it, the
three ordering regressions RED-first, the corrected docs pinned where they can be, and a green
full run.
</objective>
