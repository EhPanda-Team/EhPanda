<objective>
`buildInspectionPages` derives page display state from a live file-presence probe at inspection
time: a page is "downloaded" iff its file exists right now. That is a second display basis beside
the badge's persisted-hash count, and the two diverge in exactly the window G-15-5 exposed —
files deleted outside the app, record still claiming complete, badge saying 36/36 while the
inspector says 10 pending. 15-56/15-58 made Validate reconcile such divergence durably; this plan
removes the competing basis itself, per the owner's SSOT decision: page states derive from the
manifest (blank hash → pending, non-empty → downloaded, recorded failure → failed), so badge and
inspector read one persisted basis by construction. Pre-validate, after an external deletion, the
inspector now shows the record's claim — stale but honest to the record, consistent with the badge —
and Validate is the single tap that senses and reconciles. The scan sensor moves exclusively behind
Validate; the repair-preparation path keeps its own production scan.

The change breaks a composition 15-57 built: its widened retry basis (failed ∪ pending at the
.error/fileOperationFailed shape) gave the refusal family its start because presence-derived
pending covered externally-missing pages. Manifest-derived pending is EMPTY for a wholesale-refusal
record (hashes deliberately intact), so the union would silently collapse to nothing and the
G-15-5 dead end would return for exactly the family 15-57 fixed. D-SSOT-08 closes that: at the
operation-level-error shape the retryable basis is the FULL page set — the error is a record-wide
signal, no per-page subset is derivable from it, and the repair run's own evidence (working-seed
scan, missing-file fetch filter) decides what is actually re-fetched.

Purpose: one persisted basis behind every completeness display; the scan demoted from display
input to reconcile input, structurally.
Output: the manifest-derived buildInspectionPages, the full-set retry basis, the consumer sweep,
and rewritten pins crossing the claim-vs-disk divergence window from both sides.
</objective>

## Decisions this plan makes (owner-approved design extension, 2026-08-09)

**D-SSOT-07 — inspector page states are manifest-derived; the listing resolves resources only.**
Status precedence mirrors the current shape with the sensor swapped: non-empty recorded hash →
`.downloaded`; else recorded page failure → `.failed`; else `.pending`. The directory listing keeps
exactly one job: mapping a page index to its on-disk relativePath/fileURL so thumbnails can render
(nil when absent — a missing thumbnail under a downloaded claim is the approved pre-validate
appearance; the badge makes the same claim). The per-page existence probe is deleted. Consequence
for the UAT-5 device script, recorded for the retest: pre-validate the inspector mirrors the
manifest claim rather than sensing deletions live.

**D-SSOT-08 — the operation-level-error retry basis is the full page set.** After 15-58,
`validationErrors` means only "the last validation could not produce trustworthy evidence for every
claimed page" — a record-wide statement. Deriving a page subset from it is a category error, and
the manifest offers none (a wholesale-refusal record claims everything). The honest selection for
"retry this record whose evidence failed" is every page; `retryPages` carries it explicitly, and
the run's own production evidence re-fetches only what is actually missing while reusing usable
files through the working seed. This rewrites 15-57's D-G5C-01 union — same shape gate, wider set —
and keeps its two guarantees: the selection never depends on the record's honesty, and the basis
does not leak outside the shape.
