## D-G3-01 — the invariant this plan installs

**Teardown runs only over a still-true justifying observation. Every suspension between the
observation and the teardown invalidates it, and the observation — not merely session identity —
must be re-validated behind each one.**

In the drain branch that means: after `await pushContinuedSessionProgress(sessionID:)` (which
suspends across the `updateProgress` main-actor hop) and after the existing ownership re-check, the
branch re-asks its own question — `guard await hasPendingWork() == false else { return }` — before
`markContinuedSessionEnded`. When the re-check finds work, the branch returns and the session stays
live: the mobilizing action's work folded into this session (its own ensure was inert by design),
later flushes and convergence tails keep pushing progress, and the next genuine drain completes it.

Two recorded dependencies, stated so nobody has to rediscover them:

1. **The re-check itself must not suspend.** `hasPendingWork()` reads `activeTask`, then
   `queueStore.gids` (a synchronous `Shared` read) through `schedulableDownloads()` — same-actor
   calls with no suspension point today. The corrected doc comment must state this dependency the
   way `ensureContinuedSession` already states it for its own guard: an `await` added inside
   `hasPendingWork`'s callees later would reopen the window behind the re-check and require its own
   re-validation.
2. **One stale-shaped push is accepted and documented.** The terminal push's arguments are computed
   before the hop, so a mid-hop mobilization means the card may briefly receive a terminal-shaped
   pair ("… · 0 galleries") before the next live push corrects it. The alternative — re-checking
   before the push — cannot exist, because the push itself is the suspension. This is a transient
   string, not a state defect: the numerator floor holds, the session survives, and the very next
   convergence repaints.
