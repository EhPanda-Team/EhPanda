<objective>
Close the second half of the SC1 gap and the WR-03 warning the verification substantiated.

`delete(gid:)` cancels and clears the active task before it reads the gallery's indexed record.
When that record has vanished — an external folder deletion, a stale index repair, a concurrent
reload — the branch that handles it clears bookkeeping and returns. It notifies nobody and it never
reaches the scheduling convergence point, so the remaining queue stalls and a live session is left
either showing an empty card or slowly looking stalled until the system expires it and pauses
downloads the user never touched.

The same plan collapses the duplicated definition of "schedulable work". `hasPendingWork()` decides
whether a session starts and whether it completes; `schedulableDownloads()` decides what the card
counts. They agree today by coincidence of two hand-written copies, and nothing forces them to
change together.

Purpose: both are convergence defects. The whole session design rests on one claim — every queue
mutation exits through `scheduleNextIfNeeded()`, whose tail reconciles the session — and each of
these puts a hole in it, one by skipping the exit and one by letting two answers to the same
question drift apart.

Output: a delete whose vanished-record branch converges like every other mutation, one
actor-isolated schedulable-work authority, and two deterministic regressions covering both delete
outcomes.
</objective>

**Vanished-record delete (`DownloadClient+PublicAPI.swift`).** The branch taken when the indexed
record is gone keeps its existing cleanup — session-state clear, queue removal, background-task
removal — and then exits the way the success branch does: notify observers, then reach the
scheduling convergence point, and only then return the not-found failure. Order matters and must be
written that way: the cleanup first so the convergence pass sees settled state, the notification
before the convergence call so an observer never sees the queue move before the record disappears,
and the failure result last so the caller's contract is unchanged.

Add a comment stating why this branch cannot simply return: the active task was already cancelled
and its generation no longer owns `activeGalleryID`, so its own deferred cleanup refuses to
schedule; if this branch also declines, nothing else will, and the remaining queue plus any live
session are stranded.

**One schedulable-work authority (`DownloadClient+PendingWork.swift`).** Move the queue-and-filter
read that currently lives privately at the bottom of `DownloadClient+ContinuedSession.swift` into
this file as the module's single authority, keeping its name and its behavior exactly: read
`queueStore.gids`, read the index by those gids or read the whole index when the queue is empty,
then filter with `isSchedulableDownload`. Its doc comment states that scheduling, the pending-work
gate and the card's counts all select through it, so the set can never be defined twice.

Rewrite `hasPendingWork()` in terms of that authority. Keep the running-task fast path, but express
it as what it is — an explicitly documented additional invariant ("a running task is unambiguous
work, and skipping the disk-backed index read for it is deliberate") — rather than as a second copy
of the filtering rules. Everything below the fast path becomes an emptiness question asked of the
shared authority.

In `DownloadClient+ContinuedSession.swift`, delete the private declaration that has now moved, and
leave `schedulableProgress()` and `pauseAllSchedulable(expiring:)` calling the shared one. Their
call sites do not change.

Behavior must be identical: the two predicates are literally the same expression today, so this is
a de-duplication, not a semantic change. `DownloadPendingWorkTests` and `DownloadSchedulingTests`
are the guard on that claim and must pass untouched.
