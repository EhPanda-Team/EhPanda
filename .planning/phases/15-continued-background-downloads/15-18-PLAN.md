<objective>
Close CR-02 by fixing the rule, not the two branches the review cited.

This is the third round in which the same rule has been broken at a new site. Round 0 fixed a queued
work item that skipped scheduling. Round 3 fixed `delete(gid:)`'s vanished-record branch and wrote
the reason into a comment two lines above the branches this round has to fix. CR-02 is now the two
folder-removal catch branches of that same function — and the sweep this plan performs finds the
identical defect in `deleteFolder(name:)`, which no review has ever cited.

So the deliverable is a stated invariant plus an enumeration, not three patches:

> **ACTIVE-OWNERSHIP CONVERGENCE.** Any path that clears `activeGalleryID` or `activeTask` must
> reach `notifyObservers()` and `scheduleNextIfNeeded()` before it returns, on *every* exit path,

> is cleared, `finishActiveTaskIfOwned` fails its ownership check and returns without scheduling. If
> the clearing path also declines, nothing else will, and the queue plus its continued-processing
> session are stranded with no user-visible symptom other than downloads that never resume.

**DECISION — the added convergence is unconditional, not gated on `expiration == nil`.** This
function is also the per-gallery primitive that D-11's expiration pause-all drives, so a throwing
pause during a system expiration will now reschedule the queue the expiration is suspending. That is
deliberate, and the reasoning is written at the site rather than left to be re-derived:
  - It is not a new behavior class. This same function already converges unconditionally on the
    non-queued/active exit, `writeInitialPauseRecord` already notifies unconditionally, and the
    success path already notifies and reschedules — all of them on the expiration path too, because
    `pauseAllSchedulable(expiring:)` pauses one gallery at a time and relies on each pause's
    reschedule tail to reconcile the session. Converging on the error exit makes the error path
    consistent with the three exits around it instead of adding a fourth policy.
  - The gallery whose pause *threw* is still running or still queued. It is the one item in the
    sweep that most needs the scheduling authority, and gating convergence away from it would
    reintroduce the exact CR-02 defect class on the expiration path — ownership cleared, error
    returned, nothing left to schedule — which is the defect this plan exists to remove.
  - Re-mobilization is harmless under this phase's own contract. Nothing here starts a session: the
    convergence point schedules download work, and D-07 reserves session starts for foreground
    queue-mobilizing taps. Work scheduled as the process loses background execution suspends with
    the process and resumes on the next foreground with no visible error, which is SC3 stated
    exactly. The loop's per-iteration session and queue-intent guards still stop a stale expiration
    from pausing a successor's work.
Gating on `expiration == nil` is therefore rejected, not merely not chosen. Write the rejection and
its reason in the comment so the next reader does not re-open it as an oversight.
