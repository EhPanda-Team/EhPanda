## D-G2C-01 — the coverage count

**The gallery count pushed beside the session fraction is the denominator's coverage: the number of
galleries in the live schedulable snapshot, plus the number of `retiredSessionPages` entries whose
retired value is greater than zero. It is computed after `reconcileRetiredSessionPages`, from the
same snapshot and ledger state the fraction is summed from, by one shared helper that every subtitle
writer calls.**

Why each clause is load-bearing:

| Clause | Why |
|--------|-----|
| Live snapshot galleries all count | Each contributes its full `pageCount` to Y — they ARE the live half of the denominator. |
| Positive retirements count | D-G2-01 retirement adds a departed gallery's finished pages to both sides of every later push, so those galleries' pages are in Y. This is what keeps a completed gallery in the count — the exact device complaint. |
| Zero retirements do not count | A gallery that departed having finished nothing retires zero pages; its unfinished pages left Y with it, so nothing of it is represented by Y. The letter of the user's truth says no. This also keeps a drained nothing-was-done card honestly at zero galleries. |
| Computed after the reconcile | `reconcileRetiredSessionPages` removes a rejoining gallery's ledger entry before the live sum counts it again (the existing dedupe), so summing snapshot count + positive entries after the reconcile is double-count-free by the same construction the fraction relies on. |
| One shared helper | The diagnosis's writer census found all four production pushes flow through `pushContinuedSessionProgress`, and one more subtitle writer exists: `ensureContinuedSession`'s start submission. A single definition makes a second count basis structurally impossible. At start the ledger was just emptied, so the helper degenerates to the live count there — same value as today. |

## Decisions this plan makes

**DEC-A (resolved by the device, not by this plan): the OS does not repaint a push issued
immediately before completion.** 15-22's evidence hook proved the push fires; the round-3 device run
still showed the stale frame. This plan implements the fallback 15-22 explicitly reserved for the
owner, now authorized by the owner-articulated G-15-2C truth. The terminal push stays — under the new
basis it pushes the same count as every mid-run frame, so nothing depends on it rendering.

**DEC-B: the snapshot-internal `galleryCount` stays live-only.** `SchedulableSnapshot.sessionProgress.galleryCount`
remains `schedulableDownloads().count` — it feeds the summed-from-one-read identity and is the live
half of the coverage sum. Only the PUSHED count (and the start submission's) becomes the coverage.
The `ContinuedSessionProgress` type doc must state both roles so the internal value cannot be
mistaken for the contract.

**DEC-C: the count expression uses `count(where:)`, not a filter-count chain** — the modern API, and
it keeps the lint surface clean.
