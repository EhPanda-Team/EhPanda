<objective>
Close the reentrancy gap 15-VERIFICATION.md records against SC2 and SC3. Today the expiration
handler checks session identity once, immediately before `pause(gid:)`, and that check protects
nothing after the first suspension: the pause removes persisted queue state, awaits the cancelled
download task, and then writes a settled pause record. A resume, retry or enqueue for that same
gallery can land inside that window, report success, and be erased when the stale pause resumes.
Worse, the gallery sits in the scheduling-blocked set for the whole window, so the tap that
succeeded also fails to mobilize the queue or to start the session it asked for — the user is left
with an action that did nothing.

The fix gives every gallery a queue-intent generation that a user action advances before it writes
intent. An expiration-owned pause captures that generation with the expiring session id and re-checks
both at each post-suspension commit; when either has moved, it abandons its write. Because
abandonment means a user action is waiting behind the scheduling block, the abandoned pause also
converges once that block is lifted — notify, schedule, and let the superseded tap's session start.

Identity note (advisory assumption-delta): this adds a second identity axis beside the session id.
The session id names *who* owns a lifecycle transition; the queue-intent generation names *when* a
gallery's intent was last written by a user. They are checked together and neither subsumes the
other — a stale pause can belong to the right session and still be wrong about the gallery.

This plan also closes WR-02: the blocking fixture's runner loops until cancellation, so any early
exit before a case's final pause leaves the task running. It becomes a test-owned release token,
which is also the apparatus plan 15-15 needs to stage the interleave deterministically.

Purpose: the design's whole safety story is "the card's cancel is exactly the in-app pause". That
story breaks the moment a pause can outlive its own justification, and no existing assertion can
see it — the current foreign-id test returns at the first guard and never suspends at all.

Output: a generation-guarded, convergence-completing expiration pause, and a blocking fixture that
cannot leak.
</objective>

## Accepted residual (SC3) — visible, reasoned, and not closed

SC3's gap entry asks for expiration-owned queue writes to be protected by a generation a later user
action advances, *or* for an atomic coordinator-owned bulk transition. This plan takes the
generation route deliberately: D-11's parity claim is that the card's cancel *is* the in-app pause,
and the three existing parity cases assert that by comparing against a per-gallery pause baseline. A
bulk transition would have to re-implement the scheduling-blocked set, the manifest writes and
observer notification in step with the primitive, and the first divergence would be invisible.

The generation route is not atomicity, and this plan does not claim it is. What it guarantees:

- **Guarded.** The two suspensions an expiration pause genuinely crosses — the indexed-record read,
  and the awaited cancellation of the in-flight download task — each have an ownership check on the
  far side, before any write. The second is the unbounded one: it waits on a real download task and
  is the window every reported instance of this defect goes through.
- **Not guarded.** A user action that interleaves *inside* the first write helper's own queue-store
  hop, between that helper's in-memory intent clear and its persisted queue removal, is still
  last-writer-wins. That is a single actor hop between two adjacent statements, not a wait on
  arbitrary work, and closing it would need transactional semantics across a persisted store this
  layer does not have.
- **Consequence if it is ever hit.** The user's resume is erased and the gallery stays paused; the
  queue and the card remain consistent with each other, and a second tap recovers. No work is lost
  or duplicated, so SC3's "no lost or duplicated work" clause holds either way.

This is a deferral, not a fix, and it is recorded so it stays one: Task 1 carries it into a source
comment for the next reader of the code and into an "Accepted residual" section of
`15-14-SUMMARY.md` for the next verifier, which is an acceptance criterion of that task. A verifier
finding this window should dispose it against this record rather than raise it as a fresh gap; if it
is ever to be closed, the bulk-transition option above is the route, and it is a phase of its own.
