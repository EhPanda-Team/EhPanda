- The announcement gate is the working folder's shortfall against its manifest
  (`DownloadClient+ExecutionSupport.swift:445`), and the gate's own doc (`:387-397`) justifies
  that as equivalent to "this run has pages to fetch".
- It is not equivalent. `pendingPageIndices` (`:796-824`) opens by reading the payload's page
  selection and drops every page outside it before it ever tests file existence.
- `normalizeFetchedPayload` (`+ExecutionFetch.swift:154-186`) preserves a non-empty, in-range
  selection for every mode except the update mode, and `performRetryPages`
  (`+RetryHelpers.swift:91`) stores one with the repair mode — so the selection is live on
  exactly the route this phase treats as canonical.
- So a run can be short of its manifest while fetching a subset of that shortfall, or nothing at
  all. Trust is granted anyway, `schedulableSnapshot` (`+ContinuedSession.swift:152`) enters the
  record's FULL completed page count — N for a complete-reading record — and in the fetch-nothing
  case the run departs TRUSTED, so the retirement retires N into both sides of the fraction.

the run-scoped proof and this gate are the same predicate and must be derived from ONE
expression. That ordering constraint is directional: the proof must record the predicate, so the
predicate has to exist as a single derived expression before its lifetime can be re-owned. Fixing
G-15-26 first would force that plan to record today's shortfall binding and then force this plan
to re-point the recording — two edits to the same recording site, which is exactly the
"one lands while re-opening the other" failure both records warn against. Splitting in THIS
direction cannot reopen G-15-26: this plan does not touch where the proof is stored, only what it
is gated on, and G-15-26 stays open and unchanged at its end. 15-48 then binds to the single
expression this plan leaves behind, and its own criteria forbid introducing a second one.

Purpose: trust is rationed on work the run will really do, so the card cannot open at a gallery's
