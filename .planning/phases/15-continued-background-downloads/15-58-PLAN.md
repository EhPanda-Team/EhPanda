<objective>
15-56 made a missing-file verdict durable but deliberately kept corrupt-in-place on the refusal
surface, reasoning that a presence scan cannot license destroying the hash of a file that exists.
The owner has since decided (2026-08-09, G-15-SSOT design extension) that the reasoning was about
the wrong evidence: validate with `verifiesContentHashes: true` already produces POSITIVE
content-level evidence — a readable file whose freshly computed hash mismatches its recorded hash is
a per-page determination of the same strength as a positive absence. This plan extends the durable
reconciliation with that content arm, shrinking the refusal surface to genuinely operation-level
signals only, and revises the AGENTS.md invariant whose refusal example this makes stale.

The one genuinely new hazard is laundering, and it is verified, not assumed: the repair fetch
(`resolveSourceIfNeeded`, DownloadClient+ExecutionPerform.swift) skips a pending page whose file
exists, and `finalizeDownload`'s `addingCurrentFileHashes` merge hashes any blank-hash page from the
CURRENT file's bytes — so blanking a corrupt page's hash while leaving its file in place would cause
the next run to re-record the corrupt bytes as truth without a re-download, and validate would then
pass forever. The content arm therefore removes the provably-corrupt file under guards (D-SSOT-04),
converting corrupt-in-place into the positively-absent shape every downstream mechanism already
handles correctly — and the blanking itself still flows through the ONE existing loop, unmodified.

Purpose: collapse the last per-page state basis into the manifest — every positive per-page finding
becomes durable; only operations that could not produce evidence stay session-scoped.
Output: the content-evidence arm with combined wholesale guard and guarded removal, the rewritten
validationErrors contract, the revised AGENTS.md invariant, and the regime suite extended across the
new boundaries with 15-56's corrupt-in-place pins rewritten, not supplemented.
</objective>

## Decisions this plan makes (owner-approved design extension, 2026-08-09)

**D-SSOT-01 — positive content evidence licenses durable blanking.** A readable file whose fresh
hash mismatches the recorded hash is a positive, page-scoped determination — the exact evidence
class the blanking discipline demands — so it durably blanks that page. The refusal surface shrinks
to operation-level signals: failed scan, per-page read failure, wholesale-shape guard.

**D-SSOT-02 — the wholesale refusal applies to the content arm, over the combined set.** A
systematically wrong hash pipeline (a `fileHash` regression, an algorithm change) would mismatch
EVERY readable page; the irreversibility defence exists for exactly that class. The all-or-nothing
guard is evaluated over the combined prospective blank set (positively absent ∪ positively
mismatched) BEFORE any destructive step. With an empty mismatch set this reduces byte-for-byte to
the presence arm's existing behavior, so 15-56 is not weakened. The complementary systematic class —
the pipeline throwing on every read — produces an empty mismatch set and blanks nothing, covered by
D-SSOT-03.

**D-SSOT-03 — a read failure is a per-page hold, never blanking evidence.** The presence discipline
already distinguishes directory-level failure (wholesale refusal) from per-file non-answers
(per-page holds, D-G13-01). The content pass has no directory-level operation, so its read failure
is the per-file class: the failing page keeps its hash and its file, other pages' positive
mismatches proceed, and the `validationErrors` entry is KEPT because the pass could not classify
every claimed page. The unreadable-≡-corrupt equivalence survives only in validate's REPORTING
(the verdict message), exactly as `validatePage`'s doc states.

**D-SSOT-04 — the corrupt file is removed under guards, and why this is not optional.** Verified
from source: `resolveSourceIfNeeded` filters the pending set down to pages whose file is MISSING
before resolving a fetch, and `finalizeDownload` merges `addingCurrentFileHashes`, which hashes any
page whose recorded hash is empty from the file currently on disk. A blanked-but-present corrupt
file would therefore be skipped by the fetch and re-recorded as truth at finalize — corruption
laundered into a record that validates clean. Removal (under `validatedChildURL` containment, only
for pages the fresh pass positively established as mismatched, only after the combined guard
passed) destroys nothing recoverable — the page must be re-fetched either way — and converts the
shape into the positively-absent one, so the ONE existing blanking loop, the working-seed
preparation, the fetch filter and finalize all handle it with zero new branches. A removal failure
demotes that page to a hold (hash kept, entry kept). Ordering is load-bearing: guard, then removal,
then a fresh presence scan, then the loop — a refusal must precede the first destructive act.

**D-SSOT-05 — validationErrors is exclusively an operation-level signal.** Its contract everywhere
it is documented becomes: "the last validation could not produce trustworthy evidence for every
claimed page" — never a claim about the record. Cleared when the pass fully classified every claimed
page and any licensed reconciliation was written; kept on any hold, refusal, or thrown write. Its
displayStatus precedence hazard is unchanged and still binds: it outranks queueStore and must be
cleared at or before enqueue.

**D-SSOT-06 — AGENTS.md is revised in this plan.** The invariant's parenthetical example currently
reasons that a presence scan cannot license blanking an existing file's hash and therefore
corrupt-in-place stays session-scoped. After this plan that example is stale and would contradict
the code. The clause is rewritten to state: positive content-level evidence (a readable file whose
hash mismatches its recorded hash) DOES license durable blanking, and session-scoped state is
permitted only for operation-level signals — what the manifest legitimately cannot record.

**Deliberate residuals, dispositioned:** (a) the combined-wholesale shape still refuses and reads
`.completed` after relaunch until re-validated — the defence working as designed, re-diagnosable in
one tap, startable in-session through 15-57's widened retry; (b) if files vanish concurrently
between the guard's scan and the post-removal rescan, the loop's own guards may refuse blanking
after corrupt files were already removed — the record then over-claims until the next validate,
which sees positive absences and reconciles; hashes were never destroyed on untrustworthy evidence,
which is the property the defence protects. Record both in the summary as dispositions.
