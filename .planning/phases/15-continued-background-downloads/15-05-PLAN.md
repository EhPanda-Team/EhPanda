<objective>
Give the download coordinator ownership of the continued-processing session lifecycle, and
start sessions from the four queue-mobilizing user actions.

Purpose: D-05 makes the coordinator the session owner because it is the only place that knows
real queue state, and download-start calls already reach it synchronously from user actions.
D-06 makes the session queue-wide and singular. D-07 fixes the four submission moments. D-11
fixes the single expiration policy, which exists because the API gives one signal for both a
user cancel on the card and a system reclaim.

Output: a coordinator extension owning session start, event handling, progress arithmetic and
pause-all, wired to the four tap paths, with lifecycle coverage under automated test.
</objective>

In `DownloadClient+Scheduling.swift`, change `isSchedulableDownload(_:)` from `private` to
internal so the session extension can select the same gallery set the scheduler does. Change
nothing else about it — a divergent second predicate is exactly the bug this avoids.

Create `AppPackage/Sources/DownloadClient/DownloadClient+ContinuedSession.swift` with a
file-local `private let logger` in the module's established shape, and add `import Resources`
in sorted position if the generated localized symbols do not otherwise resolve, mirroring
`DownloadStore+Operations.swift`.

Declare `public struct ContinuedSessionProgress: Equatable, Sendable` holding a
`DownloadProgress` and an `Int` gallery count. Use this rather than a tuple: unlabeled tuple
elements are banned at error severity, and `DownloadProgress` already owns the clamping that
keeps a corrupt manifest from producing a zero or negative total.

In an extension on `DownloadCoordinator`, add:

`func schedulableProgress() async -> ContinuedSessionProgress` — read the indexed downloads the
same way the schedulable-work predicate does (queued identifiers when the queue store has any,
otherwise the whole index), filter with `isSchedulableDownload(_:)`, and sum
`completedPageCount` and `pageCount` across the survivors, counting the galleries. Build one
`DownloadProgress` from the sums so both numbers come from a single snapshot; mixing snapshots
is what makes a fraction jump.

`func continuedSessionSubtitle(for progress: ContinuedSessionProgress) -> String` — return
`String(localized:)` of the subtitle symbol, passing the clamped completed page count, the
clamped total page count and the gallery count. This function is the card's entire content
surface: it takes counts and returns a localized string, and no gallery value is in scope. Give
it a doc comment saying so, and saying why — the card renders in system UI, outside the privacy
mask and outside App Switcher snapshot protection.

`func ensureContinuedSession() async` — return immediately if `hasLiveContinuedSession` is
already true or if the schedulable-work predicate is false. Otherwise set
`hasLiveContinuedSession` to true and reset `lastPushedCompletedPageCount` to zero **before**
the first `await`, so a concurrent tap cannot slip past the guard; document that this
synchronous set is the whole guard, and that it matters because a second registration of the
same identifier terminates the app. Then take a progress snapshot, call the client's `start`
with the localized title symbol and the subtitle built from that snapshot, and store a
`Task` in `continuedSessionTask` that iterates the returned stream, forwards each event to the
event handler, and calls the end-marker once the stream finishes. The stream self-finishes, so
the task needs no external cancellation. Do not await the session being granted and do not gate
any download work on it: the work is already running, and a submission can silently never start.

`func handleContinuedSessionEvent(_ event: BackgroundProcessingEvent) async` — on `granted`,
log and do nothing, because the work is already running. On `expired`, mark the session ended
first and then pause every schedulable gallery. On `unavailable`, mark the session ended and
log at notice level only: nothing reaches a reducer, there is no error surface, and the queue
behaves exactly as it does in the foreground. Document the expiration case at length: a user
cancel on the card and a system resource reclaim arrive identically, so one policy must cover
both; the deliberate cancel is fully honored and the cost of a reclaim also leaving the queue
paused is accepted, because without a fallback tier the work could not have continued anyway.
Without that comment the uniform behavior reads as a bug.

`func markContinuedSessionEnded()` — set `hasLiveContinuedSession` to false, nil
`continuedSessionTask`, and reset `lastPushedCompletedPageCount`. It must be safe to call more
than once.

`func pauseAllSchedulable() async` — snapshot the schedulable gallery identifiers first, then
pause each one through the existing per-gallery pause primitive. Do not add a bulk mutation
path: that primitive already maintains the scheduling-blocked set, the manifest state and
observer notification, and reusing it is what makes the card's cancel literally consistent
with an in-app pause. Note in a comment that the session must already be marked ended before
this runs, because each pause reschedules and the reschedule tail will reconcile the session.

`func reconcileContinuedSession() async` — return if no session is live; if the
schedulable-work predicate is false, mark the session ended and call the client's `finish` with
success true; otherwise push progress. Give it the doc comment the deleted reconcile carried,
updated: it hangs off the single point every queue mutation converges on, so a session can
never be left running after the last download is paused or deleted.

`func pushContinuedSessionProgress() async` — return if no session is live. Take one snapshot,
compute the completed count as the larger of `lastPushedCompletedPageCount` and the snapshot's
clamped completed count so the number never regresses within a session, store it back, and
call the client's `updateProgress` with that count and the snapshot's clamped total, both
converted to `Int64`, plus the subtitle built from the snapshot. Document why the clamp lives
here rather than in the client: the client is domain-agnostic, and the scheduler's stall
heuristic reads a monotonically advancing completed count — a regressing total when a gallery
leaves the queue is legal and expected, a regressing completed count is not.

In `DownloadClient+Testing.swift`, add `public func testingHasContinuedSession() -> Bool`
returning `hasLiveContinuedSession`, in the same debug-guarded extension as the other probes.

Emit no analytics signal from any of this. `DownloadClient` has no analytics seam and none is
added here, so the expiration-driven pause rides no signal and cannot widen the closed-enum
vocabulary or the never-send list established in Phase 14.
