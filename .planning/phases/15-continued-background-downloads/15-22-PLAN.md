## D-G2B-01 — the ordering invariant this plan installs

**The drain branch of `reconcileContinuedSession` emits exactly one progress push, positioned after
the `continuedClientSessionID == nil` deferral and before `markContinuedSessionEnded`.**

The three positions and what each does:

| Position | Result |
|----------|--------|
| Before the deferral guard | Pushes with no client session to paint; the deferred reconcile would push again later. Wrong, and needless. |
| **After the deferral, before the teardown** | **Correct.** The ownership guard passes, `continuedClientSessionID` is non-nil, and `retiredSessionPages` still holds the finished work the terminal fraction is summed from. |
| After `markContinuedSessionEnded` | `markContinuedSessionEnded` clears `continuedSessionID`, so the push's own guard at the top of `pushContinuedSessionProgress` rejects it. It also zeroes `retiredSessionPages`, so even a push that passed would report a bare live sum. |
| After `backgroundProcessingClient.finish` | The store has already nilled its session id and called `setTaskCompleted`, so `updateProgress` returns at its identity guard and the task is gone. |

**Both mis-orderings are observable in tests, which is what makes this invariant enforceable rather
than aspirational.** A push after the teardown records nothing at all, so `spy.progressUpdates.last`
is still the stale pre-drain string and every terminal assertion in this plan fails. A push after the
completion is routed by the spy to `rejectedProgressUpdates` rather than `progressUpdates` — the spy
mirrors the live store's identity guard at that seam — so the terminal assertions fail *and*
`rejectedProgressUpdates.isEmpty` fails.

**A second consequence of the same change:** the drain branch's tail is currently free of suspension
points between the re-check at the top of the branch and the completion call. The push suspends
(index read, plus the ledger's record read). Ownership must therefore be re-checked between the push
and the teardown, exactly as it is after every other suspension in this file. That re-check is part of
the fix, not polish.

## Decisions this plan makes

### DEC-A — does a push immediately followed by `setTaskCompleted` repaint on device?

**Unknown, and treated as unknown.** The card is system-rendered, and this phase has been surprised by
it twice. The plan therefore does two things rather than assume an answer.

**Primary (implemented here):** emit the terminal push. Under the documented contract — `galleryCount`
is "the remaining schedulable galleries and only those" — this is a plain bug fix and yields
`"N / N pages · 0 galleries"`.

**Evidence hook (implemented here):** the drain branch logs one identifier-free `notice` immediately
after the push. Without it, a device run that still shows "1 gallery" cannot distinguish *the push was
never emitted* from *the push was emitted and the system did not repaint*, and those have opposite
fixes. The line carries no gallery value, so it stays inside the phase's log-privacy invariant.

**Fallback (NOT implemented here, deliberately):** change `galleryCount`'s basis from the live
schedulable set to the session's whole coverage, so no stale value is possible in the first place.
This is a **documented-contract change, not a bug fix**. It rewrites the `ContinuedSessionProgress`
doc comment, it changes every mid-run string the user sees, and it interacts with the base-mixing
observation recorded as `secondary_note` in `15-UAT.md` (post-ledger the pushed pair is already
session-cumulative in its fraction and live-only in its count; this would make both cumulative). It is
not the executor's call.

**Trigger for the fallback, stated so nobody has to guess:**

| Device observation after this plan lands | Verdict |
|------------------------------------------|---------|
| Final subtitle names zero galleries | DEC-A resolved: the push repaints. No contract change. Close G-15-2B. |
| Card disappears at completion without a readable final string | DEC-A resolved: satisfied vacuously — `15-UAT.md` test 2 accepts "or the card ending". No contract change. |
| Final subtitle still names one gallery **and** the drain log line is present | The push is emitted and the system does not repaint between it and `setTaskCompleted`. **Fallback triggered** — return to the owner as a new gap round proposing the contract change; do not apply it silently. |
| Final subtitle still names one gallery **and** the drain log line is absent | The push never fired. That is an ordering or guard defect in this plan's own change, not a repaint question. Fix that first and re-run. |

### DEC-B — must the terminal push be observed on a device before the phase advances?

**Yes. Device verification gates phase advancement.**

`15-VERIFICATION.md` already holds SC2 at `PRESENT_BEHAVIOR_UNVERIFIED` for precisely this reason, and
three facts make an automated-green-only advance unsafe here: the simulator neither renders the card
nor fires its cancel; this exact defect class — a terminal state no test observed — escaped the suite
twice in this phase; and DEC-A's fallback can only be triggered by a device observation. The
device-facing truth in `must_haves` is therefore a `verification: backstop`, and the summary must
record the retest inputs for `15-UAT.md` test 2 rather than claiming closure.
