<objective>
Close the client-side half of the SC1 session-lifecycle gap from 15-VERIFICATION.md: CR-01
(a submitted continued-processing request is never cancelled, so an ended session leaves an
orphan whose later launch permanently wedges the store's re-entry guard) and CR-03 (adoption
accepts any launched task, displacing a live one without completing it). Both defects share
one root — nothing at the store's end enforces the D-06 single-session assumption — and both
become provable only with a module-internal seam between the store's lifecycle logic and the
system scheduler, so this plan extracts that seam, applies the two fixes, and pins them with
a store-level regression suite.

Purpose: SC1's guarantee is currently non-durable across a process. Under D-03's queue
strategy a submission routinely sits pending while the coordinator finishes a short or
largely-cached gallery in seconds; the abandoned request later launches, the store adopts it,
and every subsequent start is refused for the rest of the process — the exact capability SC1
names, silently dead after one ordinary download.

Output: a retained-and-cancelled pending identifier, identity-checked adoption that completes
every task it rejects, a start-path seed-counter reset folded in from review finding WR-06, a
`ContinuedTaskScheduling` seam confining every scheduler verb, and regression coverage the
current suite lacks.

API coverage note: the integrated external surface remains the set enumerated in
15-RESEARCH.md § Verified API Surface. This plan invokes exactly one previously-unused verb
from that enumerated set — the scheduler's cancel-by-identifier call, named explicitly in
Task 1 — and grows the surface in no other way.
</objective>
