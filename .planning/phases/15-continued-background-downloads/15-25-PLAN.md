<objective>
Close G-15-5 (blocker, introduced by the 15-24 fix, violates SC2 and — through D-11's
stall-expiration policy — SC1). D-G4-01 grants session trust only from
`Set(downloads.filter(\.isIncomplete).map(\.gid))`, and `isIncomplete` counts the manifest's
non-empty page hashes. A `.repair` of a gallery whose record already reads complete never lowers
that count: `shouldReuseWorkingFolder` returns `true` unconditionally for `.repair`, so the working
folder survives; `ensureWorkingManifest` finds a valid manifest and returns it verbatim; and
nothing blanks hashes for pages whose files vanished. So the gid can never enter
`observedIncompleteSessionGIDs`, `isSessionWork` stays false, the gallery reports 0 session pages
for its entire run, and its untrusted departure retires 0 — a terminal card of
`0 / N pages · 0 galleries` reported with `finish(_, true)`. Per D-11 the scheduler force-expires
the tasks reporting the LEAST progress and that expiration pauses every schedulable download, so
15-24 traded a pinned-100% card for a pinned-0% one — strictly worse for SC1 liveness.

The root cause is not the trust rule; it is that the record lies. A repair exists precisely
because files are missing, yet the manifest the session reads goes on claiming every page. The gap
record offers two fix directions; this plan takes the second — **have the repair's own
file-validation result mark the record incomplete before the snapshot reads it** — because it
fixes the lie at its source instead of adding a second trust-admission channel beside the one
15-24 built. The alternative (admit a gid when its resolved start mode is a redo this session
scheduled) was evaluated against source and rejected: granting trust at schedule time makes the
basis read the manifest's full count while the folder still holds it, which for `.update` and
`.redownload` is an opening at the ceiling — exactly the D-G4-01 guarantee this plan must
preserve — and avoiding that would demand a second, file-count-based basis just for trusted
complete-reading records, a heavier rule with the same observable behavior.

**D-G5-01, the rule this plan installs: the working manifest never claims a page whose file is not
in the working folder.** `prepareWorkingSeed` — the single point every start mode's run converges
on — reconciles the working manifest against the page files actually present, blanking the hash of
every page whose file is absent, persisting and re-indexing the reconciled manifest when it
changed. The record then genuinely reads incomplete, D-G4-01's raw-counting half
(`download.isIncomplete`) covers the whole run with no arithmetic change, trust accrues through
the existing `incompleteGalleryIDs` accumulation, and the trusted departure retires the full count
at the drain. The trust set, the snapshot basis, the retirement gate, and the scheduler are not
edited at all.

Purpose: a repair's card opens at an honest zero while queued, climbs the moment the run prepares
its seed and as pages land, and drains at the full count — the stalled-task signal D-11 amplifies
cannot be produced by a repair.
Output: one reconciliation in the working-seed preparation with its rationale, a re-derived
D-G4-01 route doc, three seam-level regressions, one end-to-end ledger regression staged entirely
through production seams, and the real-page-file test support that staging requires.
</objective>

## Downstream consumers of the now-honest record — verified, not assumed

The reconciled manifest changes what `completedPageCount` / `isComplete` report for a mid-run or
interrupted repair. The executor verifies each consumer holds:

- **Run internals:** `pendingPageIndices`, `resolveSourceIfNeeded`, and
  `missingFinalizedPageIndices` are all file-existence-driven already, so the run downloads the
  same pages before and after the fix; `finalizeBatchResult` already throws
  `IncompleteDownloadError` over any missing file, so a selective repair that leaves other files
  missing refused to complete before this fix and still refuses — no behavior change there.
  `addingCurrentFileHashes` only fills empty hashes for files that exist, and finalize reaches it
  only when no file is missing, so blanked entries are always re-hashed before completion.
- **Display:** an interrupted repair's record now honestly reads incomplete → `displayStatus`
  `.inactive` instead of `.completed`, and `resumeMode`'s incomplete-inactive branch resolves
  `.repair` for it exactly as the missingFiles branch did before. This is the honest state — the
  files are genuinely missing — and it is recorded as a deliberate consequence in the D-G5-01 doc.
- **Validation:** `validatePage` skips empty-hash pages, so `storage.validate` on a blanked record
  reports `.valid` rather than `.missingFiles`; mode resolution still reaches `.repair` through
  `isIncomplete` (previous bullet), so no route is lost.
