## Warnings

### WR-01: ExcludeToggle hover and tap circle is sized by the column width and is cut only horizontally

**File:** `AppPackage/Sources/SettingFeature/EhSetting/EhSettingView+Sections3.swift:229-230` (view built at 176-197)

**Issue:** `ExcludeToggle` is a `Button` whose label is `Color.clear.overlay { glyph }`, three of them in an `HStack`
(`ExcludeRow`) inside a Form row. `Color.clear` is flexible, so the Button's rect is one third of the row (about 76 pt
wide on a 390 pt iPhone, 100+ pt on an iPad) and only as tall as the row's text (about 20 pt; the row's 44+ pt height
is list padding, not part of the view). `HoverTargetCircle` takes `max(44, width, height)`, so the diameter is the
column width, not the glyph size. `clippedAt: [.leading, .trailing]` cuts the circle at the view's left and right
only. The circle is therefore about 76 pt tall around a 20 pt view: it reaches about 28 pt above and below the view,
past the cell edge into the neighbouring language rows. D-04 records that a hover shape reaching past its own view
shows on only some List rows, and D-03 says the circle is cut "where the enlarged circle would reach a neighbouring
control"; the neighbour here is vertical. The same circle is the tap area, so the hit region is a disc of the column's
diameter rather than a glyph-sized target. Result: an oversized highlight that is clipped or missing depending on the
row, on the control whose geometry was singled out in the plan as needing the clip.

**Fix:** Give the Button a glyph-sized frame so the circle follows the glyph, and keep the horizontal clip as a
safeguard, for example inside the label:
```swift
Color.clear
    .overlay { glyph }
    .frame(maxWidth: .infinity)
    .frame(height: 44)   // row-sized, so the circle is 44, not the column width
```
or clip `.top` and `.bottom` too (`clippedAt: [.leading, .trailing, .top, .bottom]`) once the view is at least 44 pt tall.
Verify on the iPad pointer pass, in the owner checklist item for "exclusion glyphs".

### WR-02: The audit does not scan `.buttonStyle(.unhighlighted)` call sites, so an unhighlighted control can ship with no hover

**File:** `AppPackage/Tests/AppToolsTests/PointerHoverScannerTests.swift:100-114` (site kinds at 11-14);
`AppPackage/Tests/AppToolsTests/PointerHoverAuditTests.swift:71-77` (allowance)

**Issue:** D-06 says `UnhighlightedButtonStyle` "keeps drawing the label alone ... its call sites carry the helper and
the style is allowlisted". The allowlist entry exempts the style's struct, but nothing checks the call sites:
`plainButtonStyleSites` matches only `.buttonStyle(.plain)`, and `SiteKind` has no case for `.unhighlighted`. The style
draws the label alone, so it strips the system hover exactly like `.plain`. Failure scenario: someone adds
`Button { ... }.buttonStyle(.unhighlighted)` (the owner-approved way to convert a tap gesture, D-07) and forgets the
helper. The audit stays green, no control has a hover, and the failure mode the audit exists to catch (its own doc:
"the first person to see the missing hover is one with a pointer") returns. Today all five call sites carry a helper
(`CategoryView:217`, `TagSuggestionView:134`, `AppearanceSettingView:157`, `EhSettingView+Sections3:229`,
`LaboratorySettingView:83`, the last through `hoverShape` only), so the gap is latent, not live.

**Fix:** Add `.unhighlightedButtonStyle` to `SiteKind`, scan `.buttonStyle(.unhighlighted)` the same way as `.plain`, and
allow `hoverShape` for the one interactive-glass site (or allowlist `LaboratorySettingView` with a reason, as is done
for `ControlPanel`). Add a fixture for it in `PointerHoverScannerTests`.

### WR-03: The Fetch-More footer row gets a full-row highlight although only its small retry glyph is a control

**File:** `AppPackage/Sources/GalleryListComponents/GalleryList.swift:201-203` (footer at
`AppPackage/Sources/AppComponents/StateViews.swift:24-47`)

**Issue:** `FetchMoreFooter` is shown only when `footerLoadingState` is not idle (`shouldShowFooter`), that is, loading
or failed. While loading it is a `ProgressView`; the `Button` under it is `opacity(0)`, and while failed it is a
28 pt-ish icon whose frame (`.frame(maxWidth: .infinity, minHeight: 50)`) lies outside the Button, so the Button's own
tap region is the glyph. `.cellRowHover()` is applied to the whole footer, so the pointer shows the full-row
highlight in both states: on an inert spinner row, and on a retry row whose tap target is a small icon. D-04 lists
display-only rows as "not rows" and D-02 E0 covers display-only views. The grid variant (`GridList`, line 291) has no
hover on the same footer, so the two layouts also disagree.

**Fix:** Drop `.cellRowHover()` from the footer, or move it inside `FetchMoreFooter` so it applies only in the failed
state and make the Button fill the row (`.frame(maxWidth: .infinity, minHeight: 50)` inside the label with
`.contentShape(.rect)`) so highlight and tap area agree.

## Info

### IN-01: A preview helper was edited to get past the audit

**File:** `AppPackage/Sources/ReadingFeature/Support/ControlPanel.swift:418`

**Issue:** `previewControlPanel()` passed `TapGesture()`; it was changed to `DragGesture()` so the scanner stops
counting it (the helper is a plain function, not a `#Preview` body, so the preview blanking does not reach it). The
preview now exercises a different gesture than the production one only to satisfy the scanner. A scanner-driven edit to
non-shipping code is a workaround for a scanner gap.

**Fix:** Either mark the helper `#if DEBUG`-only and have the scanner blank functions it names as preview helpers, or
keep `TapGesture()` and add a one-line `ControlPanel.swift` allowance (`.tapGesture`, count 1, "preview helper").

### IN-02: Site floor equals the current census, so it has no slack

**File:** `AppPackage/Tests/AppToolsTests/PointerHoverAuditTests.swift:50-51`

**Issue:** `siteFloor = 16` and the comment says the census is 16. Converting any audited site away (for example turning
a remaining `.plain` button into a system-styled one, or removing a gesture) lowers the count and fails
`scanIsNotVacuous` although nothing is wrong. The floor guards against a broken walk; `knownMembers` already does that.

**Fix:** Set the floor a few below the census (for example 12), or drop it and keep `knownMembers`.

### IN-03: `LibraryCategoriesList.rowFill` compares two independently measured floats with `<`

**File:** `AppPackage/Sources/AppFeature/View/Library/LibraryView.swift:106` (measurement at 155)

**Issue:** `listWidth < store.viewport.width` compares the List's own `onGeometryChange` width with the width sampled by
`onVisibleViewportChange` on an ancestor. For a collapsed split view the two are meant to be equal; a sub-point
difference from rounding or a side safe-area inset on one of the two proxies would pick `.sidebarSelection`
(26 pt radius, whole cell) for a list that is drawn as inset cards. Before the first measurement `listWidth` is 0, so
the first frame is `.sidebarSelection` in the collapsed case and `.cardRow` in the sidebar case while the viewport is
still zero. Layout is unaffected (growth and shrink cancel), only the hover fill. Not provable without the device.

**Fix:** Compare with a tolerance (`viewport.width - listWidth > 1`) and treat `listWidth == 0` as unknown
(`.cardRow` only after a measurement).

### IN-04: Two hover shapes depend on context-resolved tokens or a stray indentation

**File:** `AppPackage/Sources/DateSeekFeature/DateSeekPickerView.swift:129`;
`AppPackage/Sources/SettingFeature/EhSetting/EhSettingView+Sections3.swift:231-235`

**Issue:** (a) `interactiveHover(.highlight, in: ButtonBorderShape.buttonBorder)` passes the button-border token as a
standalone `Shape`; whether its `path(in:)` outside the button's own rendering yields the glass style's capsule is not
established, and D-03 requires the hover shape to equal the visible shape. An explicit `.capsule` (or the shape the
style actually draws) removes the question. (b) The closure body of `.accessibilityRepresentation` in `ExcludeToggle`
is indented one level too deep after the Button conversion, which reads as a nesting error.

**Fix:** (a) use `.capsule` if that is what the glass `.buttonBorder` draws, and say so in the owner checklist;
(b) re-indent lines 231-235 by four spaces.
