# Quick task 261123-355: pointer hover effects — design contract

**Gathered:** 2026-11-23
**Source:** owner request (2026-11-23) to adopt an established pointer-hover pattern and implement it in EhPanda.
The rules below are that pattern, adapted to EhPanda. Items marked *(orchestrator call)* are implementation-level
choices made while adapting it; everything else is the pattern as adopted. Downstream agents treat this file as
locked: research and planning fill in the per-element inventory, they do not reopen the rules.

## Goal

Every interactive element of the iOS app shows the system pointer effect when a mouse or trackpad pointer is over
it (iPad, iPhone Duo, the app run on a Mac as an iPad app), and nothing changes at rest: no layout shift, no colour
change, no new animation. Every snapshot reference passes unchanged.

## Decisions index

- **D-01:** platform rules (system effect only, no idiom gates, iOS-only helpers, exclusions)
- **D-02:** the three effects E1 highlight, E2 lift, E0 none
- **D-03:** shape rules (visible shape, icon circle 44, text button, icon-and-label capsule, switch track, disabled)
- **D-04:** List and Form rows, rules R and S via `cellRowHover`, measured margins
- **D-05:** system-styled controls left alone, glass and borderless exceptions
- **D-06:** shared helpers in `AppTools`, existing hovers migrated, `UnhighlightedButtonStyle` allowlisted
- **D-07:** tap gestures used as controls become Buttons
- **D-08:** source audit test contract
- **D-09:** accessibility unchanged apart from D-07
- **D-10:** verification (build, tests, snapshots unchanged, owner pointer pass)
- **D-11:** gray spots locked after research (G1 to G12, margins, snapshot gate)

## D-01 Platform rules

- Use the system effect only: `.contentShape(.hoverEffect, shape)` + `.hoverEffect(.highlight)` or `.hoverEffect(.lift)`.
  Never a hand-made `onHover` fill, never a custom hover animation (the system handles timing, Reduce Motion,
  Increase Contrast and Dark Mode).
- Never gate on `userInterfaceIdiom`, device type or size class. Hover follows the input (a pointer is present),
  not the device. iPhone code is the same code; it lights up wherever iOS sends hover.
- EhPanda is iOS-only (`platforms: [.iOS(.v27)]`), so the helpers need no macOS branch *(orchestrator call)*.
- Excluded: `ShareExtension/`, preview-only code, `PreviewSupport`, `VisualSnapshotSupport`, `*_Snapshots.swift`,
  test targets.

## D-02 The three effects

| ID | Effect | Use for |
|---|---|---|
| E1 Highlight | `.hoverEffect(.highlight)` in shape S | icon buttons without a background, rows, text buttons, chips, any control inside a bar or a list, glass or tinted controls that already draw their own fill |
| E2 Lift | `.hoverEffect(.lift)` in the view's own clip shape | standalone cards or tiles with their own background that are narrower than the full content width (one rule per component, not per size: a card that becomes full width in a compact layout keeps E2) |
| E0 None | nothing; audit allowlist entry with a one-line reason | disabled controls, display-only views, full-surface gesture areas (the reader's page tap zones), a tap whose only job is to signal that something does not work yet |

## D-03 Shape rules

- The hover shape equals the visible shape: same corner radius, `.continuous` when the clip is continuous. Never
  leave the default rectangle on a rounded view.
- **Icon-only button:** a circle centred on the view whose diameter is the larger of 44 pt and the view's longer
  side (`HoverTargetCircle`). The same circle is the tap area (`contentShape(.interaction, …)`), set by the helper
  only, so the two can never drift; the view's frame does not change. Where the enlarged circle would reach a
  neighbouring control, it is cut by a straight line at the view's own bounds on that side
  (`clippedAt: Edge.Set`, `.leading`/`.trailing` following layout direction, the shape mirrors for RTL).
- **Text-only plain button:** `RoundedRectangle(cornerRadius: 8, style: .continuous).inset(by: -6)`.
- **Icon-and-label plain button:** a capsule 8 pt clear of the content on every side including the rounded ends:
  `HoverCapsule(horizontalOutset: 11, verticalOutset: 8)`.
- **Switch (rule W):** the highlight is a capsule on the switch track only (track 63×28 pt at the trailing edge,
  centred vertically, grown 6 pt on every side, mirrored for RTL), applied once inside `AppToggle`. Tapping a switch
  row's label does not flip it, so the row stays flat.
- **Disabled:** the helper reads `\.isEnabled` and applies `.hoverEffectDisabled(!isEnabled)`. A dimmed or locked
  control that still opens something keeps its hover.

## D-04 List and Form rows (rules R and S)

On iPadOS the system draws no hover on most List and Form rows, and a hover shape that reaches past its own view's
bounds shows on only some rows of a List (a `UIViewRepresentable` in a row also broke it). So the shape never grows
past the view; the row's view grows to fill the cell instead:

- `cellRowHover(_ fill: CellHoverFill = .cardRow)` on the row's outermost view: pads the content by the system's own
  row margins, frames it `maxWidth: .infinity`, `minHeight` the system row height, `alignment: .leading`, sets
  `.contentShape(.rect)`, applies E1 in a `CellHoverShape`, and sets `.listRowInsets(EdgeInsets())`. At rest the
  content sits exactly where it did.
- **R, a row in an inset card (Form, inset-grouped List):** highlight = the cell less 8 pt left/right and 3 pt
  top/bottom, corner radius 10, continuous. Variant for a List showing selection controls (edit mode): the content
  margin after the control instead of the cell edge.
- **S, a row in a sidebar-style List** (`LibraryView`'s `.listStyle(.sidebar)`): the highlight is that list's
  selection-fill shape (the whole cell, the system's continuous corner). Where that list is drawn as inset cards
  (outside the split view), it takes rule R. The width class cannot tell the two apart (split-view columns are
  compact on iPad too); use whatever EhPanda already uses to know it is in the split view, or record why the
  distinction is not needed.
- The margins are the system's on iOS 27, measured against EhPanda's own snapshot references, not copied. Starting
  values to verify: card side 20 pt, after a selection control 16 pt, card top/bottom 15 pt, sidebar side 16 pt,
  sidebar top/bottom 11 pt, minimum row height 52 pt. If any measurement differs, use EhPanda's measured value and
  record it.
- Takes `cellRowHover`: every tappable row — `NavigationLink`, `Button` and `Link` rows, menu-style `Picker` and
  `Menu` rows (the whole row), rows with a tap action. A `ButtonStyle` cannot set its row's insets, so a style used
  as a List row gets `cellRowHover()` at each call site and the style itself is allowlisted.
- Not rows: `Toggle` rows (rule W), text fields, display-only rows, disabled rows, and rows whose system hover
  already looks right (verify, then record).

## D-05 System-styled controls

Leave controls the system already hovers alone, and never stack a second `.hoverEffect` on them: `.bordered`,
`.borderedProminent`, toolbar items, `Link`, `Toggle` (beyond rule W), default `Picker`/`Menu`, List selection rows.
Known exceptions from the adopted pattern, to apply where EhPanda has the same case:
- `.glass` / `.glassProminent` buttons **outside a toolbar** show no pointer effect: give them E1 in their own
  capsule/circle/rounded shape via `hoverShape(_:)` or `interactiveHover(.highlight, in:)`.
- `.borderless` buttons **inside a list row** show no pointer effect: text → the text-button shape, icon → the icon
  circle.
Any other system-styled control that turns out flat under the pointer gets E1 in its border shape, recorded in the
summary.

## D-06 Shared helpers (single home, `AppTools`)

One file in `AppPackage/Sources/AppTools/` *(orchestrator call: `AppTools` already imports SwiftUI and
`AppToolsTests` already hosts the source-scan suites)*, public API:
- `enum InteractiveHoverEffect: Sendable { case highlight, lift }`
- `View.interactiveHover(_ effect: InteractiveHoverEffect, in shape: some Shape)` → `contentShape(.hoverEffect,
  shape)` + `hoverEffect(...)` + `hoverEffectDisabled(!isEnabled)`
- `View.hoverShape(_ shape: some Shape)` → only `contentShape(.hoverEffect, shape)`, for a system-styled control whose
  own hover has the wrong shape; never adds a second effect
- `View.interactiveIconHover(clippedAt: Edge.Set = [])` → `HoverTargetCircle` as both the interaction and hover shape
- `View.cellRowHover(_ fill: CellHoverFill = .cardRow)`
- Shapes: `HoverTargetCircle(clippedAt:)` (min diameter 44, `layoutDirectionBehavior: .mirrors`, a clipped circle is
  the circle intersected with the rect grown past the other edges), `CellHoverShape`, `HoverCapsule`, the switch
  track shape; the row-margin constants in one enum.
- Existing hand-written hovers (`CheckboxToggleStyle`, `ChoiceCard`, `CommentModerationMenu`, `BlockedCommentCard`)
  move onto the helpers with the same shapes.
- `UnhighlightedButtonStyle` keeps drawing the label alone (owner decision 2026-09-15 on the designed look); hover
  changes nothing at rest, so its call sites carry the helper and the style is allowlisted.
- Doc-comment the why of every non-obvious choice (bounds-limited shapes, the cell margins, clipped circles).

## D-07 Tap gestures used as controls

An `.onTapGesture` that acts as a control becomes a `Button` (with `.unhighlighted` where the designed look must be
kept) so VoiceOver and Voice Control see a button, then takes the matching helper. A gesture that is not a control
(the reader's page zones, a dismiss-tap over a full surface) is E0 and allowlisted.

## D-08 Source audit (test contract)

A Swift Testing suite in `AppToolsTests` (reusing `RepositoryWalk`) scans iOS-compiled app code (`App/**` and
`AppPackage/Sources/**` minus the D-01 exclusions):
- every `.buttonStyle(.plain)`, `PlainButtonStyle()`, `.onTapGesture`, `TapGesture` and `SpatialTapGesture` must have
  `interactiveHover(`, `interactiveIconHover(` or `cellRowHover(` in the modifier chain that follows it (a gesture
  value inside a modifier call such as `.simultaneousGesture(…)` counts the chain after that call);
- every `struct … : ButtonStyle | PrimitiveButtonStyle` must have one of them in its body;
- otherwise the site is on an allowlist entry `(file, kind, count, reason)`; an entry whose count no longer matches
  fails as stale, an entry without a reason fails;
- the scanner blanks comments, string literals (raw, multiline, interpolations) and non-ASCII bytes, and evaluates
  `#if` for iOS (`os(iOS)` true, other `os(…)` false, `canImport(AppKit)` false, other `canImport`, `DEBUG` and
  unknown flags true);
- a floor on the number of sites found, so a broken path or filter cannot pass vacuously;
- no file outside the helper applies `contentShape(.interaction, HoverTargetCircle…)` by hand;
- scanner fixture tests for each rule above, and shape unit tests for `HoverTargetCircle` (44 pt minimum, longer side
  wins, each clipped edge stops at the bounds, both-sides clipping keeps width and full height, no point beyond a
  clipped edge).

## D-09 Accessibility

Hover changes nothing VoiceOver reads. The only accessibility changes are D-07 conversions, which gain the button
trait (and `.isSelected` where the row represents a selection). Keyboard focus rings and Full Keyboard Access are out
of scope.

## D-11 Gray spots locked after research (orchestrator calls, 2026-11-23)

A pointer cannot be driven by automation here, so no task depends on a pointer probe. Where the system's own effect
is uncertain, the call follows the adopted pattern's own on-device survey, and the D-10 owner pass is the check.

- **G1 (default-styled and `.borderless` Buttons outside List rows):** system-styled (D-05): the system draws their
  hover. Add only `hoverShape(<visible shape>)` where the visible shape is not a plain rectangle (Home card,
  preview, tag chip, archive card, grid cell, history cell: use each one's real radius and style). Do not add
  `interactiveHover` or `.hoverEffect` to them, and do not change their button style. Each such group is listed in
  the summary's owner checklist with "if flat: follow-up".
- **G2, G4 (Library sidebar):** rule S applies (`cellRowHover(.sidebarSelection)`); the adopted pattern found the
  sidebar rows flat. Resolve to rule R where the list is drawn as cards; the discriminator is existing state
  (`store.viewport` / `usesSidebar`), never a size class. Record what was measured.
- **G3 (glass):** `Glass.interactive()` controls are system-styled (no helper; at most `hoverShape` if the shape is
  wrong). Non-interactive glass outside a toolbar (`.glass`, `.glass(.clear)`, `.glass(.regular.tint(...))`,
  `.glassProminent`) takes E1 in its glass shape per D-05.
- **G5–G12:** take the research file's proposed mapping as written (G7 rating drag: E0, not audited; G8 inline
  Picker options: system; G12: route the raw `Toggle` through `AppToggle`).
- **Margins:** measure as the research file describes; use measured values; record them in the helper's doc comment
  and the summary.
- **Snapshot gate:** a local candidate run on the pre-change tree, then a compare run on the changed tree, both
  under the pinned visual environment from the research file. Any moved pixel at rest is a defect to fix, not a
  baseline to re-record.
