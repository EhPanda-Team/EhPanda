## Summary

The tree has few places that need a *hand-written* hover and many that need the row/shape rules. Counted from source:
9 `.buttonStyle(.plain)` sites, 2 `.onTapGesture`, 4 tap-gesture values (2 `TapGesture` in `GalleryReadInteraction`, 2
`SpatialTapGesture` in the reader), 3 custom `ButtonStyle` structs, 25 `AppToggle` sites, one raw switch `Toggle` row,
about 60 Form/List rows that are tappable (`Button`, `Link`, menu `Picker` rows), 8 glass buttons outside toolbars, and
4 glass/clip hybrids (`glassEffect(...interactive())` on a plain `Button`). Two shared edit points cover every gallery
list: `GalleryList.DetailList` (rows) and `GalleryList.GridList` (grid), used by 8 screens plus Downloads.

Three facts shape the plan. (1) The audit chain direction: D-08 wants the helper in the modifier chain **after**
`.buttonStyle(.plain)`; today `BlockedCommentCard` and `CommentModerationMenu` put their hover **inside the label**
(before the style), so they must move outward when they move onto the helpers. (2) `quickSearchFeature`,
`filtersFeature` and `systemNotification` do not depend on `AppTools` in `Package.swift`; each needs the dependency to
use the helpers. (3) There are no committed snapshot references and no approved baseline, so "references pass
unchanged" means a local candidate run on the pre-change tree, then a compare run on the changed tree, on the pinned
simulators (commands below). List margins are not recorded anywhere in the repo; the executor measures.

**Primary recommendation:** build the helper file and its tests first (Wave 0), run a 10-minute pointer **probe** on an
iPad simulator to settle what default-styled buttons and the sidebar List draw (gray spots G1, G2), then convert by
feature group with a snapshot compare per group.

## Architecture Patterns

### Hover-shape ownership (one rule for the planner)

```
what the element is                     -> who draws the hover        -> helper
custom/plain/gesture/unhighlighted        helper (E1/E2/E0)             interactiveHover / interactiveIconHover
List/Form/sidebar row                     helper, fills the cell        cellRowHover (R / S)
switch                                    AppToggle, once               rule W shape
default/bordered/toolbar/Menu/Picker      system                        none, or hoverShape(shape) if rounded
glass button OUTSIDE a toolbar            helper, own shape (D-05)      interactiveHover(.highlight, in:)
```

Scanner traps found while reading:

- Token matching must be identifier-bounded. `onSingleTapGestureEnded` (`GestureHandler.swift:48`), `UITapGestureRecognizer`
  (`LiveTextView.swift:177`) and `SpatialTapGesture` all contain `TapGesture`; `\bTapGesture\b` skips the first two and
  `SpatialTapGesture` needs its own pattern. The Live Text recognizer is a UIKit tap on the reader surface: E0, not audited.
- `GalleryReadInteraction` is shared by row cells (`GalleryList.swift:180`, `DownloadsView+Subviews.swift:417`) and
  grid cells (`GalleryList.swift:272`, `DownloadGalleryItem.swift:94`). The hover differs by use (R vs grid shape), so
  the two `TapGesture` values inside it are an allowlist entry `(GalleryReadInteraction.swift, TapGesture, 2, reason)`
  and the helper goes on each call site. Its `.buttonStyle(.borderless)` is not an audited token.
- Four `.buttonStyle(.plain)` sites currently have the hover **inside** the label (`BlockedCommentCard.swift:70-71`,
  `CommentModerationMenu.swift:240-241`) or none (`ReadingToolbar.swift`, `LibraryTitleMenu.swift`, `View+Toast.swift`,
  `CommentsView.swift`, `ControlPanel.swift:86`). The chain after the style is what the audit reads, so the helper goes
  right after `.buttonStyle(.plain)` and before any later padding (for `CommentModerationMenuButton` before
  `.padding(.vertical, -12)`/`.padding(.trailing, -12)`, which overhang the row and must not move the hover shape).
- `#Preview` bodies and free `previewX()` helpers are compiled in the app targets. The scanner has to either blank
  `#Preview { }` blocks or the plan has to allowlist/avoid them (ControlPanel is the only preview site found).
- There is no `*_Snapshots.swift` file in the tree (`find` returned none); the D-01 exclusion is vacuous but harmless.
  `VisualSnapshotSupport` and `PreviewSupport` are separate Sources modules; `AppFeature/UITestSupport/` holds no
  audited token.

**Confirmed (from the repo):**
- No committed snapshot reference exists: `git ls-files` finds no baseline/reference PNG, and
  `AppPackage/Tests/VisualSnapshotTests/Baseline/` is absent (`Scripts/visual/README.md`, "Baseline" status: not yet
  created; images were removed from history per `SIDEBAR-BACKGROUND.md` header). No file records a row margin, cell
  inset or minimum row height. All six starting values in D-04 (20, 16, 15, 16, 11, 52) are **unconfirmed here**.
- The Library sidebar list is never drawn outside a `NavigationSplitView`: `LibraryCategoriesList` is only built by
  `LibrarySidebarView` (`LibraryView.swift:51-53`), and the stack case (`.other`, narrow Duo) shows no list at all, only the
  title menu. `HEADER-STABILITY.md:74` records that `List(.sidebar)` **outside** a `NavigationSplitView` "renders a
  grouped list" `[VERIFIED: .planning/quick/261015-tx1-.../HEADER-STABILITY.md:74]`, which is the case rule S->R exists
  for; EhPanda does not produce it in production.
- How EhPanda decides sidebar vs stack: `LibraryFeature.State.usesSidebar` (`LibraryFeature.swift:16-22`), verbatim
  `case .pad, .none: true`, `case .other: false`, `case .duo: viewport == .zero || device?.supportsLandscapePanes(in: viewport) == true`.
  `device` comes from `WindowDeviceObservation` (`.pad` when `userInterfaceIdiom == .pad`, `WindowDeviceObservation.swift:63`),
  `viewport` from `.onVisibleViewportChange`. It is reducer state at `LibraryView` level; **no environment value reaches the list**. `HorizontalPaneWidths`
  is the reader's and Home's pane-width struct, unrelated. `WindowDevice.pad` stays true in a narrow iPad window, so
  `usesSidebar` stays true while the `NavigationSplitView` may be collapsed to a stack.
- Because the list is always the split view's sidebar column, rule S applies in production. The **open** case is a
  collapsed split view (iPad Slide Over/narrow Stage Manager window): is the same list drawn as sidebar rows or as inset
  cards there? `[ASSUMED]` unknown. **Proposal (G2):** executor measures both; if they differ, discriminate with the list's
  own width (`onGeometryChange`) against `store.viewport.width` (already published by `LibraryView.swift:36`), not with a size class.

**Executor must measure** (nothing derivable from the repo): in a plain `Form` row, a `GalleryAnchoredList` row, the QuickSearch
edit-mode row and a sidebar row, on iPhone Air and iPad Pro 11 M5, portrait and landscape, text sizes `xSmall`/`large`/`AX5`:
card side margin, top/bottom margin, margin after the edit-mode control, minimum row height, sidebar side/top/bottom, and

## Don't Hand-Roll

| Problem | Don't build | Use instead |
|---|---|---|
| hover effect | `onHover` fill, custom animation | `contentShape(.hoverEffect, ...)` + `hoverEffect(...)` (D-01) |
| disabled hover | per-site `isEnabled` checks | the helper reads `\.isEnabled` once |
| RTL | manual leading/trailing flips | `Shape.layoutDirectionBehavior = .mirrors`, build the clipped circle in LTR geometry (leading = minX) |
| swapping a system control's effect | a second `.hoverEffect` | `defaultHoverEffect(_:)` or `hoverShape(_:)` |
| tap target for icon buttons | `contentShape(.interaction, HoverTargetCircle...)` at call sites | only inside the helper; the D-08 audit forbids it elsewhere |

## Common Pitfalls

1. **Hover inside the label, style outside.** The audit reads the chain after the style; keep helpers outside (above).
2. **`.listRowInsets` placement.** It must reach the List row container; inside `DownloadListRow`/`DownloadGalleryItem` it is a single
   view per row, so it works, but never put the row helper inside a `ForEach` that yields several views per element.
3. **Pinned downloads source tests.** `DownloadsSwipeActionSourceTests` (`AppPackage/Tests/DownloadsFeatureTests/DownloadsSwipeActionSourceTests.swift`)
   reads `DownloadGalleryItem.swift` and brace-matches from the anchors `.swipeActions(edge: .trailing`, `.swipeActions(edge: .leading`,
   `.contextMenu`, `var managementMenu:`, `var row:`, `var grid:`, and counts `role: .destructive`, `.tint(.red)` and `deleteButton(role:` inside those
   regions. Adding a hover modifier to `grid` or to `DownloadListRow` does not touch the counts; do not add a brace-bearing comment or a
   second `.contextMenu` inside those regions, and do not rename the anchors.
4. **`ReduceMotionGatingSourceTests` pins by token count per file** (`AppPackage/Tests/AppToolsTests/ReduceMotionGatingSourceTests.swift`):
   `accessibility` + `ReduceMotion` reads (25 total), `reduceMotion ?` predicates (36), mentions of `reduceMotion` (80 total) and `numericText` sites (11). A hover helper adds none of these, **but** the
   four pinned files that move onto the helpers (`CheckboxToggleStyle.swift` 1/1/2, `ChoiceCard.swift` 1/1/2, `View+Toast.swift` 1/1/3, `CommentsView.swift` 1/2/3)
   and every file converted from a tap gesture (`LaboratorySettingView`, `EhSettingView+Sections3`) must keep their reads/mentions identical.
   Re-run `-only-testing:AppToolsTests`; re-derive a table only if a line mentioning `reduceMotion` moved.
5. **Comment/blank rules.** `RepositoryWalk` and `ReduceMotionGatingSourceTests` filter only whole-line `//` comments; the D-08
   scanner needs real comment/string blanking (block comments, `///`, multiline and raw strings) and `#if` evaluation, so it cannot reuse that filter.
6. **`Capsule()`/`Circle()` as an argument is banned by lint** (`shape_initializer_argument`, `.swiftlint.yml:311-318`): pass `.capsule`, `.circle`, `.rect(...)`.
   A chained call is allowed, so `RoundedRectangle(cornerRadius: 8, style: .continuous).inset(by: -6)` passes; custom shapes (`HoverCapsule(...)`) are not in the regex.
   Prefer `.rect(cornerRadius:)`, which is `.continuous` by default `[ASSUMED]`; use the explicit `style: .continuous` form where the existing clip says so.
7. **Rows under Dynamic Type.** The row helper's `minHeight` and margins must hold at AX5, where `GalleryDetailCell` stacks cover over text and `leadingInset` goes to 0 above `.large`.
8. **Confirmation dialog anchors.** Logout, Reset Filters, Clear Cache, Remove Custom Translations, Delete Profile: `cellRowHover` wraps the Button chain *after* the dialog modifier, or the dialog stays on the Button; never hoist it to the Form.
9. **Hidden controls.** `visible(_:)` pairs opacity with accessibility; the Detail favourite pair (`DetailView+HeaderSection.swift:205-219`) always has one invisible control. Confirm hover does not light the invisible one.
