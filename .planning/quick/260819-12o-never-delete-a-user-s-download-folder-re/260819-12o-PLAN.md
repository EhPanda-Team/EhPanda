<objective>
Guard one invariant end to end: **the download client never deletes a gallery folder it did not itself create in the same run.** The only production violator is the completion sweep — `completeDownload` → `removeSupersededFolders(gid:token:keeping:)` (`DownloadClient+Execution.swift:82-105`), which walks `storage.galleryFolderURLs(gid:token:)` (any folder matching by `[gid_token]` prefix OR by manifest gid/token, including one the user renamed in Files.app) and removes every folder but the completed one. Confirmed on iPad multitasking: a Files.app rename with a stale index + Repair/Resume recreates the folder at the old name, refetches everything, and the sweep then deletes the user's renamed folder. Retire the sweep (D-1) and, with it, the repair-seed materialization whose whole purpose was "carry the old folder to the re-addressed destination, then let the sweep delete the old one" (D-2). Add no rename resolution (D-4). Pin the invariant with a full-arc test (D-5), correct the docs the change makes false (D-6), and record the decision under G-15-2H (D-6).

Purpose: a user's download folders are user-managed through Files; nothing the app does on its own may remove one.
Output: three commits on `feature/gsd-phase-15` — `fix(15): never delete a user's download folder`, `test(15): pin a duplicate folder survives a run`, `docs(15): record the sweep retirement in G-15-2H`.

**PN-1 The delete/keep boundary inside "repair seed".** Two different things share the word "seed". The **repair seed** (`RepairSeed`, `RepairSeedContext`, `repairSeed(for:payload:)`, `materializeRepairSeed`, `linkOrCopyReadableAsset`, and the source-side unprobed-page carry) copies an OLD folder's files into a differently addressed destination — DELETE. The **working seed** (`WorkingSeed`, `prepareWorkingSeed`, `prepareWorkingSeedAnnouncingProgress`, `PreparedWorkingRun`, `authorizedReconciliationScan`, `reconcileWorkingManifestAgainstPageFiles`, `recoveredBlanking`, the cover `discardingRejected: true` at `+ExecutionSupport.swift:519`) scans and reconciles the run's OWN destination folder — KEEP. Doc sentences that say "working seed" (`DownloadInspection.swift:64`, `+ExecutionFetch.swift:187`, `+PersistenceNormalize.swift:234,414`, `+SeedReconciliation.swift:25`) refer to the kept half and stay as they are.

Every one of the 39 `existingDownload:` argument lines under `AppPackage/Tests` belongs to that shim (verified: the count of `existingDownload:` lines in Tests equals the count of shim calls), so the mechanical deletion is safe to script (see Task 1). `performDownload` keeps its own `existingDownload` (used for the execution context / cover).
