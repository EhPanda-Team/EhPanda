<objective>
Make every gallery list fetch and every gallery detail fetch that a reducer starts reach the network only through one
injectable TCA dependency, `GalleryClient`, so a test decides each outcome deterministically. Then remove the three
`.errorSurfaced` stopgap filters quick task 261121-ifi added, so those tests assert the full signal list again, and
correct every comment that explained them wrongly.

The 261121-ifi explanation was wrong. A pushed screen's fetch never reached the network under the test host: the test
network guard (`AppPackage/Sources/TestNetworkGuard/TestNetworkGuard.m`, linked into every package test target by
`Package.swift`'s `testTarget(module:)`) fails every unstubbed non-loopback request offline at once. The real defect is
that reducers construct the request struct inside their effects, so a test cannot choose the outcome. The guard turns
the request into `.networkingFailed`, which since 261121-ifi raises `errorSurfaced` at a moment set by effect
scheduling, and that races `skipInFlightEffects(strict: false)`. In TCA 1.26.2 that call only clears the test store's
set of tracked effects. It neither cancels the effects nor waits for them.

Purpose: tests that start a gallery fetch state its outcome and assert it exactly. Nothing in the app changes.
Output: the `GalleryClient` module, 22 reducer call sites in 11 files moved onto it, the test changes, and
`261121-m6q-SUMMARY.md`.
</objective>

### Design (decided at planning; orchestrator direction where stated)

- **One `GalleryClient` struct in a new module, `AppPackage/Sources/GalleryClient`**, depending on `.appModels`,
  `.networkingFeature` and `.composableArchitecture`. The four consuming modules are Home, Favorites, Search and
  Detail, and each already depends on NetworkingFeature. Favorites, Search and Home depend on Detail, and none of
  them depends on another. A client inside one feature, as HomeClient, LoginClient and ReportFormClient are, would
  force the other three to depend on that feature or to duplicate the client. NetworkingFeature stays the request
  layer. It declares no `DependencyKey` today, and its tests drive the requests directly. DFClient and DownloadClient
  already sit over NetworkingFeature in their own `…Client` modules, so the new module follows that precedent and
  the module = type naming convention.
- **One client, not separate list and detail clients.** The Favorites and Detail modules start both kinds of fetch.
  The test value is unimplemented per closure, so a test that overrides one fetch is still told about any other.
  A second dependency key would add nothing.
- **Closures mirror the requests one to one** (orchestrator: each closure is the dependency seam). Parameters keep
  the request initializer's argument order. Results are the request's `response()` type. Every closure is
  `@Sendable … async throws(AppError)`. The live bodies are `private static func`s bound by reference, as LoginClient
  does: the typed throws survives, and the long parameter lists stay inside the 120-column limit.
- **Values (orchestrator direction, HomeClient pattern).** `liveValue` is `.live`, `previewValue` is `.noop` and
  `testValue` is `.unimplemented`. `unimplemented` uses `IssueReporting.unimplemented("GalleryClient.<closure>",
  throwing: AppError.unknown)` so the issue names the closure. `noop` answers with empty results and a not-found
  detail, because a detail has no empty value. A fourth value, `failing(_ error: AppError) -> Self`, fails every
  closure with `error` and reports nothing. It is the stub for a fetch a test starts but does not care about.
  `noop` and `failing` are built by two file-private generic closure factories, `returning(_:)` and `throwing(_:)`.
  These are not wrappers: they replace 28 hand-written typed-throws closure literals. No public memberwise
  initializer is added, because nothing outside the module builds a client from scratch. Tests mutate the `var`
  closures.
- **HomeClient stays as it is.** It is the capture scenes' seam for the Home root, and its popular fetch arranges the
  carousel. Routing its live value through `GalleryClient` would make one dependency resolve another and is not
  cleaner. **DownloadClient stays as it is.** It is already an injected dependency, and its detail request carries
  its own session and cellular policy.
- **Exact assertion across concurrent effects.** In each stopgap test, the stubbed failure's `errorSurfaced` and the
  test's navigation signal (`homeSectionViewed`, `galleryDetailOpened`) are sent by two `.run` effects that run
  concurrently, so their relative order is undefined. Each of these tests therefore waits for every effect with
  `finish()`. It asserts the recorded list as two exact partitions, `errorSignals` and `nonErrorSignals`, which
  together are the whole list. No signal is dropped, and no cross-signal order is assumed.
- **One shared partition (orchestrator amendment).** This is the partition 261121-ifi added privately to
  `SearchFeatureTests/AnalyticsEmissionTests.swift`. Task 1 moves it, once, into the shared test module
  `TestingSupport` as a public extension on `[AnalyticsSignal]`, deletes Search's private copy, and has the Search,
  Home and Downloads emission suites import `TestingSupport`. Two copies would otherwise become three. Graph evidence
  for the new `TestingSupport → AnalyticsClient` edge, checked at planning:
  - **Test-only module.** `TestingSupport` is excluded from the package products (the `products:` filter in
    `Package.swift`). The only targets that depend on it are five test targets: AppFeatureTests, ParserFeatureTests,
    DownloadsFeatureTests, ImageClientTests and ReadingFeatureTests.
  - **No cycle.** No source target depends on `TestingSupport`. AnalyticsClient's own dependency closure is AppModels,
    AppTools, Resources, OSLogExt, CookieClient, DeviceClient and external packages, so nothing in it can reach back.
  - **Link cost.** ImageClientTests is the one existing consumer that does not link AnalyticsClient today, so it now
    links AnalyticsClient, CookieClient, DeviceClient and TelemetryDeck transitively. FeatureTests builds all of them
    anyway. ParserFeatureTests already links AnalyticsClient through AppFeature, and the other three consumers depend
    on it directly.
