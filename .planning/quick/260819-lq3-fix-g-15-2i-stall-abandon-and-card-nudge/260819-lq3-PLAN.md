## Planner design decisions on the SUGGESTED items (owned here — reasoning stated, do not re-litigate)

**PD-1 Where "last byte" is stamped, and how idle time is measured.** `InFlightPageTransfer` gains `var lastByteDate: Date?`, reset to `nil` in `beginPageTransfer` (per attempt, like `firstByteDate`) and stamped in `recordPageTransferBytes` when `bytesWritten > 0`, from the SAME `now()` read that stamps `firstByteDate` and on the same path that grows `creditedSubunits` (`DownloadClient+PageTransferProgress.swift`, the `bytesExpected > 0` credit block sits right below). Idle time is one definition on the entry: `func idleInterval(at date: Date) -> TimeInterval { date.timeIntervalSince(lastByteDate ?? startDate) }`. The sweep computes it once per transferring entry and applies both thresholds to it: `>= pageTransferAbandonThreshold` → abandon; else `>= pageTransferStallThreshold && !stallLogged` → the existing "still transferring" line. Consequence, deliberate: the sweep's 10 s log now also names a MID-transfer silence (bytes then nothing for 10 s), which is the same starvation the 60 s rule abandons; the line's wording ("N ms without bytes") stays true. `endPageTransfer`'s exit check is left exactly as it is (`firstByteDate == nil`): its documented concern is "ended having never received a byte", and generalizing it would make a normally completed transfer whose last write-to-finish gap exceeded 10 s log as starved.

**PD-2 Two constants, not one.** `pageTransferAbandonThreshold: TimeInterval = 60` is added beside `pageTransferStallThreshold = 10` in `DownloadClient+Manager.swift` (line ~66). The log stays sensitive at 10 s, the action stays conservative at 60 s. Doc on the constant says so, and names the owner decision date.

**PD-3 How abandonment triggers the retry — the existing PAGE retry path, not `withRetry`/`retryLimit`.** The spec suggests counting against `retryLimit = 3`; that constant governs `withRetry`, which page transfers deliberately bypass (`downloadAndSavePage` passes `retriesRequest: false`, `DownloadClient+PageDownloadHelpers.swift`). The page's actual retry path is `downloadPage`'s attempts loop (`context.options.autoRetryFailedPages ? 2 : 1`, default on), which re-resolves the image URL through the failover request (`resolvedImageSource(failover:)`) — a fresh URL, potentially a different image host, which is exactly the right remedy for a hung host and is the "same page continuing" that `beginPageTransfer` documents (credit kept via `max`). So an abandoned attempt surfaces out of `rawPageDownloadResponse` as `AppError.networkingFailed` — retryable, honest ("the network stopped delivering"), already the error every other transport failure of a page maps to — and nothing new is added to `AppError`. Consequences, stated plainly: with auto-retry on (default) a persistently starved page fails after two attempts ≈ 2 × (60–70 s) ≈ 120–140 s plus resolution latency; with the user's auto-retry OFF it fails after one attempt ≈ 60–70 s, like every other network failure under that setting — the setting governs. A transfer the SYSTEM defers (discretionary background transfer) for more than 60 s is treated exactly like a hung one — abandoned, retried, then failed and left retryable through the record's retry surface; this is inside the owner's binding 60 s decision and is not special-cased. `withRetry`, `retryLimit` and `AppError` are untouched.

**PD-4 The cancel handle: each attempt runs as a `Task` the entry holds.** The coordinator has no handle on the URLSession task (`hub.wait` cancels it through Swift task cancellation), so `rawPageDownloadResponse` wraps `pageDownloader.download(...)` in `let attempt = Task { ... }` (NOT detached: it inherits the actor's priority and hops off at the first await inside the nonisolated downloader), attaches it to the entry (`attachPageTransferAttempt(gid:pageIndex:_:)`, a named function so the attach reads as the entry's lifetime step it is), and awaits it under `withTaskCancellationHandler { try await attempt.value } onCancel: { attempt.cancel() }` so the CALLER's cancellation (pause, expiry sweep, group cancel) still reaches the transfer. The sweep's `abandonPageTransfer(gid:pageIndex:idle:)` runs on the actor and, in one synchronous stretch: sets `isAbandoned = true` and `stallLogged = true` on the entry, logs through the ONE existing helper `logStarvedPageTransfer(... outcome: "abandoned")` (no new masked log site — the privacy census stays at 2 for that file), then calls `attempt?.cancel()`. In `rawPageDownloadResponse`'s catch of a cancellation-shaped error the order is: `Task.isCancelled` → rethrow `CancellationError` (the caller cancelled; unchanged behaviour); else entry `isAbandoned == true` → throw `AppError.networkingFailed`; else rethrow `CancellationError` (a system-side cancel, unchanged). `beginPageTransfer` resets `isAbandoned = false` and `attempt = nil` for the next attempt. `sweepStarvedPageTransfers` skips entries already `isAbandoned` (the cancelled attempt closes on the next actor turn) and stays in the heartbeat file, made internal (drop `private`) so the testing seam can drive it; no second timer is added. Boundary, stated in the sweep's doc: abandonment is a heartbeat action, so it exists exactly while a live session's card is at stake — which is the case the ruling covers and the case observed.

**PD-5 Half 2 shape — the reporter lives in the STORE (`ContinuedProcessingSession`), one flag crosses the seam.** Adapted from a reference project's reporter value type (never named; content reproduced name-free): a value type holding the last measurement and the consecutive-nudge count; an unchanged measurement adds one unit; any change snaps back and clears; headroom is reserved above the highest measurement so a finished-looking measurement can still be nudged; the nudge is logged so a device log tells real progress from the workaround. Two deliberate departures, both required by this app: (i) the cap is 30 consecutive nudges (owner, BINDING) rather than the reference's headroom-sized cap; (ii) the denominator stays `pages × subunitsPerUnit(1000)` — this app's units are meaningful integers and `ContinuedProcessingSessionTests` pins that semantics — so headroom is `cap + 1 = 31` sub-units held back above the highest measurement (`min(completed * 1000 + inFlight, total * 1000 - 31)`, floored at 0), NOT a 2^53 fraction scale. Why the store and not the coordinator: the store owns the system `Progress` and its own doc says it is "the only place that can express a value the caller's vocabulary cannot"; the stalled-report predicate (`clamped measurement == last clamped measurement`) is then computed from the very values published, in ONE place, and every push — flush, intra-page, convergence, heartbeat — flows through it, so a real change from ANY push snaps back and a non-heartbeat identical push cannot dip below `measured + nudge`. Only heartbeat reports may INCREMENT the nudge — the owner's cap is stated "at the 10 s heartbeat", and intra-page identical pushes arrive at up to 1 Hz on a crawling page, which would spend the cap in 30 s — so the seam carries one Bool, `nudgesWhenStalled`, true only from `beatContinuedSession`. The heartbeat's existing line-96 comparison is a log throttle against the last LOGGED summary (30 s minimum), not a per-beat predicate, so it is left as the log rule it is; the reporter's comparison is the single stalled-report predicate. Why the seam's FOURTH slot becomes a struct: `function_parameter_count` is 5 and `updateProgress` already has 5, so the `Int64` in-flight slot becomes `ContinuedSubunitReport { inFlightSubunitCount: Int64 = 0, nudgesWhenStalled: Bool = false }` (public, `Equatable, Sendable`, declared beside `BackgroundProcessingSession` in `BackgroundProcessingClient.swift`); the store's `updateProgress(sessionID:completedUnitCount:totalUnitCount:subunits: = .init(), subtitle:)` defaults it, so `ContinuedProcessingSessionTests`' calls need no edit, `DownloadContinuedSessionExpirationTests`' hand-built double keeps its `{ _, _, _, _, _ in` arity, and the `DownloadSourceInventoryTests` label/`Task.yield()` censuses do not move.

**PD-6 The 30-nudge cap re-derived against a 509 back-off — verdict: the cap holds, and a longer wait is NOT held open.** This app performs no in-run 509 back-off wait: a 509 arrives as a placeholder image (`quotaExceededImageURLSuffixes`, `ImagePlaceholderFingerprint.quotaExceeded`) → `AppError.quotaExceeded` → `isFatalAccountAppError` → the batch aborts and the run fails; the queue moves or drains. So the "back-off can exceed five minutes" premise names no wait this app makes. The longest legitimate flat stretch is a page starving through its attempts under Half 1: ≈ 2 × 70 s ≈ 140 s (+ resolution). 30 nudges at 10 s ≈ 300 s is more than double that. Past the cap the published count goes flat ON PURPOSE: the system reclaims the session (~30 s later) and the existing expiry arm pauses schedulable downloads — a wedged queue cannot hold the session forever, which is the guarantee the owner wanted the cap to carry. This rationale goes verbatim (in prose) into `ContinuedProgressNudge`'s doc, together with the note that any future in-run wait longer than the cap (none exists) must publish progress of its own or re-derive the cap.

**PD-7 File-length gates.** `DownloadClient+ContinuedSession.swift` is at 997/1000; Task 2 adds ~6 lines there (the `nudgesWhenStalled` parameter wraps the signature, and the report construction is three lines taller than the five positional arguments it replaces). Relocate `continuedSessionSubtitle(for:)` VERBATIM with its full doc comment (`/// The card's entire content surface …` through the closing brace, ~19 lines) into a new `DownloadClient+ContinuedSessionSubtitle.swift` (imports `Foundation`, `Resources`; a `// MARK: - Continued Session Subtitle` extension of `DownloadCoordinator`) — the ONLY relocation; both callers (`ensureContinuedSession`, `pushContinuedSessionProgress`) are unchanged. `DownloadContinuedSessionTests.swift` is at 995: its three seam calls change on ONE line each (`0` → `.init(inFlightSubunitCount: 0)`, `250` → `.init(inFlightSubunitCount: 250)`; both stay under 120 columns) — `wc -l` must stay < 1000 for both files after the edit. `DownloadPageTransferProgressTests.swift` (317) takes the Half 1 cases; `ContinuedProcessingSessionFoldTests.swift` (119) takes the Half 2 end-to-end cases; the pure reporter cases go in a new `ContinuedProgressNudgeTests.swift`.

**PD-8 What the spy records.** `BackgroundProcessingClientSpy.ProgressUpdate` replaces `let inFlightSubunitCount: Int64` with `let subunits: ContinuedSubunitReport` plus a computed `var inFlightSubunitCount: Int64 { subunits.inFlightSubunitCount }`, so the seven existing `.inFlightSubunitCount` reads compile unchanged and the one construction site (`DownloadProgressSeriesGuardTests.makeSeries`) changes one line (`inFlightSubunitCount: 0` → `subunits: .init()`).
